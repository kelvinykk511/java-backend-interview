# InnoDB 主鍵：自增 vs UUID（頁分裂）

## 面試題
InnoDB 表點解唔建議用隨機 UUID 做主鍵？分佈式場景又唔想用自增，點揀？

## 答案要點
- **聚簇索引**：InnoDB 數據按主鍵順序存喺 B+ 樹葉子頁（16KB）。
- **自增**：新行永遠插喺最右邊嘅頁，寫滿就開新頁 → 順序寫、頁填充率高（~15/16）、buffer pool 只需熱住最右幾頁。
- **隨機 UUID**：插入位置隨機 →
  1. **頁分裂**：插入已滿嘅中間頁，要拆一半搬去新頁，多 I/O + 加鎖，頁只剩一半滿 → 空間浪費、碎片。
  2. **隨機 I/O + buffer pool 命中率跌**：要改嘅頁散落成棵樹，數據大過內存就頻繁讀盤。
  3. **體積大**：`CHAR(36)` 36 字節 vs `BIGINT` 8 字節；**每個二級索引葉子都存一份主鍵** → 所有索引一齊變大。
  4. 字符串比較慢過整數比較。
- **分佈式揀法**：
  - **雪花 ID（Snowflake）**：64 位、趨勢遞增，主流選擇（要處理時鐘回撥）。
  - **號段模式**（美團 Leaf / DB 批量取號）。
  - 一定要 UUID：用 **UUIDv7 / 有序 UUID**（時間戳喺前），存 `BINARY(16)`；MySQL 8 `UUID_TO_BIN(uuid, 1)` 可將 v1 嘅時間位調前。
  - 業務唯一鍵（訂單號等）做**唯一二級索引**，主鍵仍用自增 / 雪花。

## 常見追問 / 陷阱
- **自增嘅坑**：
  - 暴露業務量（訂單號連續可被爬）→ 對外用另一個 ID。
  - `innodb_autoinc_lock_mode`：8.0 預設 2（交錯），配合 ROW binlog 冇問題；用 STATEMENT binlog 時批量插入可能主從 ID 唔一致。
  - 自增值唔連續（回滾、插入失敗都會消耗），唔好當「無缺號」用。
  - 8.0 之前自增值只喺內存，重啟按 `MAX(id)+1` 重算可能重用已刪 ID；8.0 起持久化到 redo。
  - 單表分庫分表後自增會撞 → 步長 / 全局 ID。
- **熱點**：極高併發插入時自增全部撞最右一頁（latch 競爭），通常唔係瓶頸，真係撞就分表。
- 冇定義主鍵 → InnoDB 用第一個非空唯一索引，再冇就用隱藏 6 字節 `DB_ROW_ID`（全局共享計數器）。
