# READ COMMITTED vs REPEATABLE READ（InnoDB）

## 面試問題

InnoDB 默認 RR，什麼時候改成 RC？兩者在鎖與一致性上差在哪？

## 答法

**一眼對照**

| | READ COMMITTED (RC) | REPEATABLE READ (RR，默認) |
|---|---|---|
| 快照 | **每條語句**新開 Read View | **事務開始**（首條非鎖讀）定快照 |
| 不可重複讀 | 可能（他事務提交後你再讀到新值） | 同事務內同行一致 |
| 間隙鎖 | 普通 `SELECT` 幾乎不加；**當前讀**仍可能 | 當前讀常用 Gap / Next-Key 防幻讀 |
| 典型場景 | 短事務、高併發寫、減少 gap 死鎖 | 報表式一致讀、要「整段事務同一視圖」 |

**面試怎麼說**

- RR：適合「這一單處理期間，我看到的基礎數據別飄」；代價是範圍更新/插入更容易 **gap 死鎖**（昨日 Next-Key 那題）。
- RC：Binlog 行格式下很多互聯網業務改用 RC，**少 gap 鎖 → 少插入死鎖**；接受「同事務兩次讀可能不同」。
- 兩者 **當前讀**（`SELECT … FOR UPDATE` / `UPDATE`）都走鎖，不是「RC 就完全沒鎖」。

**和 MVCC 的關係**：隔離級別主要影響 **Read View 何時建立** 以及 **當前讀加什麼鎖**；不是兩套完全不同的引擎。

## 常見追問 / 陷阱

「改成 RC 就不會死鎖？」

→ 不會。行鎖衝突、鎖順序反了照樣死鎖；只是 **空隙上的插入意圖鎖對撞會少很多**。

另一陷阱：在 RR 下用「普通 SELECT」當庫存判斷，再 UPDATE —— 快照與當前讀不一致，要麼當前讀，要麼樂觀版本號。

## 小練習

高併發「搶券 UPDATE stock = stock - 1 WHERE id=? AND stock>0」，你傾向 RC 還是 RR？理由用「鎖範圍」講一句。
