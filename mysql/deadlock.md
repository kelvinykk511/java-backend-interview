# InnoDB 死鎖：成因、檢測與避開

## 面試問題

InnoDB 為什麼會死鎖？發生後資料庫怎麼辦？應用要怎麼寫才能少踩？

## 答法

**什麼是死鎖**

- 兩個（以上）事務互相持有對方想要的鎖，形成環等待 → 誰也走不下去。
- 典型：A 改 row1 再改 row2；B 改 row2 再改 row1（加鎖順序相反）。

**InnoDB 怎麼處理**

- 有 **死鎖檢測**（預設開）：發現環就 **回滾代價較小的一方**（通常 undo 較少的事務），另一方可繼續。
- 被犧牲方拿到錯誤（如 `Deadlock found when trying to get lock; try restarting transaction`）→ **應用應重試**（有限次數 + 冪等）。

**怎麼查**

- `SHOW ENGINE INNODB STATUS\G` 看 `LATEST DETECTED DEADLOCK`。
- 慢查詢 / 監控裡抓死鎖頻率；對照 SQL 與索引（沒索引 → 鎖範圍變大 → 更容易死鎖）。

**怎麼少踩（實務口條）**

1. **同一組資源固定加鎖順序**（例如一律先小 id 再大 id）。
2. 事務 **短小**：少在事務裡做 RPC / 睡線程。
3. 索引命中，避免掃太多行；RR 下 gap/next-key 會放大衝突面。
4. 熱點行（餘額、庫存）考慮隊列串行或樂觀鎖版本號，別一堆長事務搶同一行。
5. 捕獲死鎖異常 → 有限重試；不要無限重試打爆 DB。

## 常見追問 / 陷阱

「把隔離級別改成 RC 就不會死鎖？」

→ 不會。RC 少用 gap lock，**某些**死鎖會變少，但 row lock 互等照樣死鎖。治本仍是加鎖順序 + 短事務 + 好索引。
