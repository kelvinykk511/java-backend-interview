## 上次 drill 答案（2026-11-25）

題：出金服務同時出現兩件事：

A) 發佈後一個交易 Pod CPU 飆到 100%。`top -Hp` 見到幾條高 CPU 線程名叫 `GC task thread`／`G1 Conc`；另外一條 `http-nio-8080-exec-` 都好高，`jstack` 停喺對用戶備註欄做 `Pattern.matches(userMemo)`。同事即刻喺呢個未摘流量嘅 Pod 跑 `jmap -dump`，另一個建議「先把 `-Xmx` 加大頂住」。

問：你會點分「業務死循環」同「其實係 GC／內存」？呢個時候即刻 dump、加大堆，有咩風險？備註欄嘅正則可能係咩問題？你嘅排查順序係咩？

B) 出金流程：Try 凍結餘額 → 調簽名機（可能超時）→ Confirm 真扣並記 txid；失敗就 Cancel 解凍。出現三種時序：(1) Try 超時，協調者發咗 Cancel，但遲到嘅 Try 之後先到；(2) Confirm 第一次其實成功咗，呼叫方超時又重試咗 3 次；(3) 簽名已廣播上鏈，有人主張用 Saga「補償：加返餘額」或者乾脆改 XA 2PC 打通錢包庫同訂單庫。另外有同事話「用 Outbox 發一條扣款消息就夠，唔使凍結」。

問：三種時序各會出咩資金問題？狀態機要點擋？Outbox 替代唔替代到凍結？鏈上已廣播點解唔能只靠 Saga 補償？你會點揀？

- **先分規模，再對堆棧**。`GC task thread`／`G1 Conc` 高 CPU，先當**內存／分配問題**，唔好只當業務死循環。用 `jstat -gcutil` 睇老年代同 FGC 係咪持續爬；Full GC 後回唔到穩定水位先考慮洩漏。
- **同時可以有業務熱點**。`http-nio-8080-exec-` 停喺 `Pattern.matches(userMemo)`：`matches` **每次都 compile** 正則，本身已食 CPU；用戶備註係不可信輸入，惡意／複雜字串可以觸發**災難性回溯（ReDoS）**，單線程打滿一核。所以呢個 case 兩邊都可以同時發生。
- **未摘流量就 `jmap -dump`**：dump 要入 safepoint，會 **STW**；交易高峰等於自己製造一次長停頓，大堆寫盤亦有磁碟風險。應先從 LB 摘就緒，再 dump。
- **加大 `-Xmx` 救唔到洩漏**，只係延遲爆炸，而且 Full GC 更長。若主因係正則，加堆完全唔對症。
- **排查順序**：`top` 分單核 vs 全核（亦要對照 cgroup 配額）→ `top -Hp` + tid 轉 nid → `jstack` 重複 2–3 次（或 Arthas／火焰圖）→ GC 線程熱就查 GC log／堆，摘流量再 dump → 正則改預先 `Pattern.compile`、限制備註長度同複雜度、避開易回溯寫法。

- **(1) Cancel 先到、遲到 Try**：若 Cancel 見到「未見 Try」就當無單忽略，遲到 Try 之後凍結成功 → **懸掛凍結**（錢凍住冇人解）。正確做法係 Cancel 做**空回滾**：即使未見 Try 都先記 `CANCELLED`；遲到 Try 見到已取消就拒絕／唔凍結。
- **(2) Confirm 已成功又重試 3 次**：Confirm 必須按 `txId` **冪等**。狀態已係 CONFIRMED 就直接成功返回，唔可以再扣一次，否則**重複扣款**。
- **(3) 簽名已廣播上鏈**：鏈上轉帳不能 rollback（最多再上一筆反向交易，唔係加返用戶賬本就當冇發生過）。Saga「補償：加返餘額」會令用戶同時有鏈上幣同賬本餘額 → 超發。XA 2PC 亦無法把錢包庫同區塊鏈放進同一個原子提交。廣播後狀態應係「待鏈上確認」，禁止 Cancel、禁止補加餘額；等確認數／處理 reorg，用對賬兜底。
- **Outbox 替代唔到凍結**。Outbox 只保證本地事務提交後消息一定會出，唔負責喺長耗時下游（簽名機）期間預留資金。無凍結時，並發出金可以超額。
- **點揀**：出金用 TCC（或等價預留）+ 以 `txId` 做狀態機（空回滾、冪等 Confirm、遲到 Try 拒絕）；鏈上已廣播就唔好補償加款；對賬兜底。唔好用 XA 打通鏈。
