# 2026-11-20 Java warm-up

## 上次 drill 答案（2026-11-19）

題：下單鏈路同時出現兩件事：

A) 調風控用 Apache HttpClient。服務端 keep-alive timeout 30s，客戶端關咗取出驗證、idle timeout 設 60s；有個攔截器讀完 response headers 就 return，body 喺異常路徑經常冇 consume。另外每個請求 `HttpClients.createDefault()`。高峰期池看起來耗盡，大量請求卡在借連線，偶發 `NoHttpResponseException`，本機仲見到好多次完整 TLS 握手。有人建議把池同 Tomcat 線程各加一倍，並且對所有 reset 自動重試 3 次（包括下單）。

B) 用戶持倉用一個 Hash `pos:{uid}`，活躍做市商可以有幾萬個 field。對帳任務 `HGETALL pos:{uid}` 之後 `DEL pos:{uid}` 再重建；過期同覆蓋寫亦用 `DEL`。開盤時呢個 Redis 節點 RT 飆高、replica 落後，Cluster 入面就呢個 node 內存特別高。有人話「呢個係 hot key，加一層本地 Caffeine 就得」。

問：(1) A 裡面邊啲做法令 Keep-Alive 失效、連線洩漏、偶發 reset？池同線程、重試你會點改？(2) B 係 big key、hot key，定兩者都有？點解本地緩存救唔到 `DEL`？定位同拆／刪你會點改？

- **每次 `createDefault()`：Keep-Alive 形同虛設**。每個新 `HttpClient` 都係一個新池；唔 close 就洩漏，close 咗下一個請求又重新建連，所以會見到大量完整 TLS 握手。應該共用一個長期活著嘅 client／連線池。
- **body 冇 consume：連線還唔返池**。連線要等實體讀完（或明確 abort）先可以重用。攔截器只睇 headers 就 return，異常路徑唔 consume，池就「借走唔還」或留下半開連線，高峰卡住借連線。用 `EntityUtils.consumeQuietly`／try-with-resources，保證成功同失敗路徑都 consume。
- **server 30s < client idle 60s，又關取出驗證**：伺服器已關掉嘅連線仲留喺客戶端池，再借出嚟用就 `NoHttpResponseException`。client idle／TTL 要**短過** server keepalive（例如 20–25s），並開 stale eviction 或取出後校驗。
- **池同 Tomcat 線程各加一倍唔對症**：根因係無複用同連線洩漏，唔係容量不夠。線程加多，只會更狠噉搶一個已經髒／洩漏嘅池。先修複用同歸還，再按下游客量定池大小，並設 acquire 超時 fail-fast。
- **對所有 reset 重試 3 次（包括下單）**：讀請求先可以有限重試；下單非冪等，reset 唔等於上一筆一定失敗，盲目重試可能重複下單。下單靠冪等鍵，唔好對寫操作自動重試。HTTP/2 多路複用可以減少連線數，但唔等於可以靠更長 Keep-Alive 去避開過期連線。
- **B 首先係 big key，開盤時可以兩者都有**。幾萬 field 令單 key 體積大，`HGETALL`／`DEL` 都係 O(N)，呢個 node 內存偏高、主線程被卡住、複製緩衝堆積 → replica 落後。開盤若集中打呢個做市商，同時可以係 hot key。本地 Caffeine 只能擋**讀**，擋唔到對帳／過期／覆蓋嗰下 `DEL`——大刪除仍然打中 Redis 主線程同複製鏈。
- **定位**：`--bigkeys` 只報每類型**元素數**最大嘅 key，value 好大嘅 String 可能漏，要配 `--memkeys`／`MEMORY USAGE`／RDB 分析。再對呢個 node 睇 slowlog（`HGETALL`／`DEL`）、RT、replication lag。
- **拆／刪**：Hash 按 field 分片（`pos:{uid}:{shard}`），Cluster 要令新 key 分散到唔同 slot；讀用 `HSCAN`／`HMGET`，禁止開盤路徑 `HGETALL`。刪用 `UNLINK` 或 `HSCAN` + 分批 `HDEL`，開 lazyfree。重建寫新 key 再原子切換，舊 key `UNLINK`，唔好 `HGETALL` + `DEL`。設計期限制集合大小。

詳見 [HTTP Keep-Alive 與連線池](../networking/http-keepalive-connection-pool.md)、[Redis Big Key](../redis/big-key.md)。
