# 2026-11-21 Java warm-up

## 上次 drill 答案（2026-11-20）

題：入帳鏈路同時出現兩件事：

A) 主庫名義上「雙 1」。故障演練先 `kill -9` mysqld（磁碟同 OS cache 還在），之後又做一次拔電。有人為咗 TPS 把 `innodb_flush_log_at_trx_commit` 改成 2，並話「已經開咗 semi-sync，雙 1 可以關」。同事認為「雙 1 之下，進程崩潰同拔電結果一樣」。

B) 充值事件用 `uid` 當 Kafka key。Producer 開咗冪等，但 callback 失敗時應用會再 `send` 一次；消費者拉到之後丟線程池並發入帳，失敗就扔到 retry topic，成功先後無保證。後來分區由 12 擴到 24。出現同一用戶先見到「入帳成功」再見到「入帳中」，偶發重複入帳。

問：(1) 進程崩潰 vs 拔電，雙 1 同只把 `flush_log` 改成 2，主庫同 binlog 一致性有咩差別？semi-sync 能唔能替代雙 1？(2) 點解冪等 producer 救唔到 B？key、消費並發、重試同擴分區你會點改？

- **雙 1 之下，進程崩潰同拔電結果先「一樣」**：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`，每次提交 redo／binlog 都 `fsync`，兩種故障都一致、已提交事務唔丟。同事呢句只喺雙 1 成立；換成其他刷盤參數就唔同。
- **`kill -9` ≠ 拔電**。進程崩潰時 OS cache 通常會被刷落盤，所以只把 `flush_log` 改成 2（每次 write 到 OS cache、約每秒 fsync）多數**唔會丟**。拔電／kernel panic 先會暴露未 fsync 嘅約 1 秒 redo。
- **只改 `flush_log=2`、保留 `sync_binlog=1`，拔電會分叉**：binlog 可能已落盤、redo 未 fsync → 從庫／Canal 有呢筆，主庫恢復後冇（下游通知到、主庫餘額冇加）。相反，`flush_log=1` + `sync_binlog=N` 係主庫有、binlog 尾部冇。雙 1 就係為咗堵兩個方向。
- **Semi-sync 替代唔到雙 1**。Semi-sync 等至少一個從庫 ack binlog（進 relay log），降低「主庫已提交、從庫未收到」喺主掛切從時嘅丟失；**替代唔到**本機 redo／binlog 落盤。超時仲會退化成異步。資金庫兩者都要。Group commit 可以令雙 1 仍然有吞吐，唔好為 TPS 亂關。
- **冪等 producer 救唔到 B**。佢只保同一 producer 會話、由客戶端重試嘅不重不亂。Callback 再 `send` 係一條**新紀錄**（新序號），會排到後面，既亂序又可能重複。
- **`uid` 當 key**：同一用戶有序，但大戶變熱點分區。入帳狀態機更宜用 `depositId`；要按用戶串行就本地按 key 哈希到固定線程，而唔係把所有事件塞同一分區。
- **消費線程池**打斷分區內順序；失敗丟 retry topic，後續消息可能先完成，所以會見到「成功」再生「入帳中」。同 key 要同線程／隊列，或暫停該 key；再加狀態機（`UPDATE ... WHERE version < ?`／合法狀態轉移）。
- **12 → 24 分區**：`hash(key) % N` 變咗，同一 `uid` 新舊消息可能並行消費。有序 topic 預先規劃分區；必須擴就先停寫／排空，或接受短暫窗口靠版本號。
- **重複入帳**：at-least-once + 應用再 send + retry topic + 下游冇唯一鍵。用 `depositId` 唯一約束／去重表兜底。

詳見 [redo log、binlog 與兩階段提交](../mysql/redo-binlog-two-phase-commit.md)、[Kafka 消息順序](../kafka-mq/message-ordering.md)。
