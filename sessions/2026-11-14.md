# 2026-11-14 Java warm-up

## 上次 drill 答案（2026-11-13）

題：行情網關：本地 Caffeine TTL=1s + Redis 物理 TTL=3s，key 係 `ticker:BTCUSDT`。20 個 Pod 幾乎同一時間啟動，本地同 Redis 過期時間齊。miss 時用 Redis `SET NX PX=200ms` 做重建鎖；搶唔到鎖嘅請求喺 Tomcat 線程上忙等，直到搶到或 3 秒超時。重建查庫要 500ms。問：(1) 一次對齊過期，大約會打中 DB 幾次？(2) 點解 Tomcat 會先被打滿，而且 Redis CPU 仍然很高？(3) 你會點改（進程內 singleflight、鎖 TTL、邏輯過期、過期抖動）？

- **打中 DB 次數**：鎖 200ms < 重建 500ms，鎖會提前過期，下一個請求會再開一輪查庫。若搶到鎖後有再 GET 緩存，一次對齊過期大約 **⌈500/200⌉ = 3 次**；若忙等只為搶鎖、搶到就查庫不再讀緩存，在途請求會輪流拿到鎖，次數可以接近在途請求數。唔會係 1 次，亦唔等於 Pod 數 20（Redis 鎖仲有序列化，但太短）。
- **Tomcat 先滿、Redis CPU 仍然高**：忙等佔住請求線程，最長 3 秒，對齊過期一瞬間就把 Tomcat 打滿，接口先 503。所有等待者緊密循環打 `SET NX`，20 個 Pod 打同一個熱 key，Redis 單分片 CPU 被輪詢打高——鎖只串行化重建，擋唔住狂問鎖。
- **點改**：進程內 singleflight（同一 JVM 同一 key 只一人去 Redis／DB）；鎖 TTL 要大於重建時間（或續期），等到超時／搶到鎖都要再讀緩存，禁止喺 Tomcat 上 busy-spin；邏輯過期（物理不過期，value 帶 expireAt，過期仍回舊行情再異步重建）；Caffeine／Redis TTL 加隨機抖動，避免多 Pod 對齊過期。

詳見 [熱點 Key 重建](../redis/hot-key-rebuild-stampede.md)。

## 今日 drill

對帳 job 用 offset 循環掃當天成交，同線上共用主庫：

```sql
SELECT * FROM trades
WHERE trade_time >= ? AND trade_time < ?
ORDER BY id
LIMIT :offset, 1000;  -- offset 每次 +1000
```
