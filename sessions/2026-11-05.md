# 2026-11-05 Java warm-up

## 上次 drill 答案（2026-11-04）

題：Java 服務調下游 HTTPS，壓測 P99 好高，CPU 大量花喺加解密，抓包見幾乎每個請求都有一次完整 TLS 握手。邊度出問題？點改？

- **根因：連接冇被重用**，每個請求新 TCP + 新 TLS 握手（非對稱加密 / 密鑰交換係貴嘢）。
- **常見原因**：
  - 每個請求 `new` 一個 `HttpClient` / `RestTemplate`（底層連接池跟住 client 走，用完就冇）。
  - **response body 冇讀完 / 冇 close**（Apache HttpClient、OkHttp），連接還唔到池，池滿就開新連接。
  - 連接池太細（Apache 預設每 route 最多 2–5 條），併發一高就超出池嘅連接用完即棄。
  - 對方或中間 LB 回 `Connection: close` / keep-alive 超時比你短。
  - `HttpURLConnection` 呼叫 `disconnect()`。
- **改法**：client 做單例 bean、配好連接池（max total / per route）、`try-with-resources` 消費並關閉 body、設 idle 回收同 keep-alive 時間短過服務端；抓包 / 日誌確認連接重用。另外 TLS session 恢復（1.2 session ticket、1.3 PSK）可減輕重握手成本，但根治係重用連接。

詳見 [HTTP keep-alive 與連接池](../networking/http-keepalive-connection-pool.md)、[HTTPS / TLS](../networking/https-tls-basics.md)。
