# 2026-11-24 Java warm-up

## 上次 drill 答案（2026-11-23）

題：下單／出金鏈路同時出現兩件事：

A) `OrderService.place()` 標咗 `@Transactional`（REQUIRED）。入面調另一個 Bean 嘅 `wallet.debit()`（都係 REQUIRED）。debit 拋 `InsufficientFundException`（RuntimeException），place 把它 catch 住，再調 **同一個類** 嘅 `this.logFailure(...)`（方法上標咗 `REQUIRES_NEW`），然後 **唔 rethrow**，直接 return 失敗碼俾前端。另外有人把 outbox `INSERT` 拆去 `recordEvent()`（另一 Bean，`REQUIRES_NEW`），理由係「失敗都要留事件」。

問：會唔會出現 `UnexpectedRollbackException`？失敗審計會唔會留下？outbox 呢種拆法有咩後果？你會點改傳播、調用方式同 catch？

B) 同一個 Redis 實例 `maxmemory-policy=allkeys-lru`，同時放：訂單詳情緩存（TTL 10 分鐘）、出金鎖（`SET NX PX 30s`）、一個**永不過期**嘅交易對配置 Hash。某日緩存變大，`evicted_keys` 飆升、`expired_keys` 平穩，鎖提早消失導致重複出金。同事改成 `volatile-lru` 之後，配置 Hash 還在，但寫入開始報 `OOM command not allowed`；`INFO memory` 仍然很高，其中有一批已經到期嘅冷緩存。

問：點解釋呢三個現象（鎖提早沒、改 policy 之後 OOM、過期 key 仲佔內存）？`volatile-lru` 救唔救到鎖？你會點改部署同政策？

- **會出現 `UnexpectedRollbackException`**。`debit()` 同 `place()` 都係 REQUIRED，共用同一個事務。RuntimeException 一拋出，Spring 已把呢個事務標成 **rollback-only**；就算 `place` catch 住唔 rethrow、正常 return，提交時仍然會失敗。
- **`this.logFailure` 自調用，`REQUIRES_NEW` 無效**，審計走同一個已 rollback-only 嘅事務，**失敗審計留唔到**。若經另一個 Bean（真代理）做 `REQUIRES_NEW`，審計會獨立提交，之後 `place` 仍然丟 `UnexpectedRollbackException`。
- **Outbox 用 `REQUIRES_NEW` 係錯嘅「留痕」**：業務下單／扣款會滾回，事件卻已獨立提交，Relay 可能當成功單去出賬。成功事件必須同業務同一 `REQUIRED` 事務。「失敗都要留痕」應該用獨立審計表 + 經代理嘅 `REQUIRES_NEW`，唔好同出金／下單 outbox 混。
- **改法**：唔好喺 `@Transactional` 方法裡吞 RuntimeException。用一個無事務嘅門面 catch，再分別調業務方法，同經代理／另一 Bean 嘅 `REQUIRES_NEW` 審計。自調用要改 self-inject、`AopContext.currentProxy()` 或拆 Bean。成功 outbox 搬返同一個事務。

- **`evicted_keys` 升、`expired_keys` 平穩 = 內存滿被淘汰**，唔係 TTL 到期。`allkeys-lru` 會淘汰所有 key，包括出金鎖 → 鎖提早沒，重複出金。
- **`volatile-lru` 救唔到鎖**：鎖有 TTL，一樣喺可淘汰集合裡。它只保住**冇 TTL** 嘅配置 Hash。
- 配置 Hash 常駐又佔空間，可淘汰嘅只剩帶 TTL 嘅緩存／鎖，釋放唔夠 `maxmemory` 就 `OOM command not allowed`。
- 過期 key **讀唔到係準時**（惰性刪），內存釋放靠定期抽樣，冷嘅過期 key 會滯留，所以 `INFO memory` 仍然高。
- **改法**：鎖、緩存、常駐配置分實例；緩存用 `allkeys-lfu`／`lru` 且每個 key 有 TTL；鎖／配置用 `noeviction`。業務層仍要唯一鍵／狀態機。
