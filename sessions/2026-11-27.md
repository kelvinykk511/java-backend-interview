## 上次 drill 答案（2026-11-26）

題：出金／行情同時出現兩件事：

A) 出金寫主庫後，同一 `@Transactional` 方法入面再 `SELECT` 訂單狀態，中間件把 SELECT 打去從庫；前端 200ms 後刷新列表亦打從庫。半同步已開，`Seconds_Behind_Source` 多數係 0，但仍有用戶「下完單列表係空，一秒後先出現」。同時對帳大報表打同一條交易從庫，延遲突然跳高。

問：點解半同步 + `Seconds_Behind_Source=0` 仍然會讀唔到？事務內把 SELECT 拆去從庫仲有咩問題？讀路徑同報表你會點拆？

B) 熱更新交易開關：

```java
class Switch {
  boolean stop = false;
  Config cfg;
  volatile Config published;
  void update(Config n) {
    n.limit = 100;
    cfg = n;
    published = n;
  }
  void loop() {
    while (!stop) {
      Config c = cfg;
      use(c.limit);
    }
  }
}
```

另外有人用 `volatile int seq; seq++` 做 client 序號。

問：`loop` 可能見到咩狀態？點改先算安全發布？`stop` 同 `seq++` 各有咩問題？

- **半同步唔解決讀延遲**。`AFTER_SYNC` 只保證至少一個從庫已把事件刷入 **relay log**，**唔保證 SQL／worker 已 apply**。寫完即刻讀從庫，本來就可以係空。半同步超時仲會退化成異步。佢解決嘅係「主掛咗，已提交數據唔丟」，唔係 session 一致性。
- **`Seconds_Behind_Source=0` ≠ 已追平**。呢個數字靠時鐘同「最後一條已執行事件」估算：主從時鐘偏差可以顯示 0；大事務重放期間會失真；並行複製下更唔準。應用 pt-heartbeat，或比較主從 GTID executed set。
- **事務內把 SELECT 拆去從庫更糟**。同一個 `@Transactional` 入面自己啱寫嘅行，從庫既睇唔到未提交嘅寫，亦可能未 apply 啱提交嘅寫 → 一定空／舊。動態數據源／中間件要「事務內強制主庫」，唔可以按「SELECT 就走從」做語句級路由。
- **改讀路徑**：寫後關鍵讀走主（同一次請求內，或該用戶寫後 N 秒 sticky）；或寫完拿 GTID，讀從庫前 `WAIT_FOR_EXECUTED_GTID_SET`，超時 fallback 主庫。下單／出金接口最好直接返回已寫入嘅數據。餘額、凍結、訂單狀態以主庫為準。
- **報表／對帳** 要隔離到專用從庫，唔好同交易讀共用一條 replica，否則 apply 被慢查拖住，所有寫後讀一齊出事。

- **`loop` 讀非 volatile 嘅 `cfg`**：可以一直見到舊對象，或者見到新引用但 `limit` 仲係預設值（寫線程雖然先改欄位再賦引用，但讀 `cfg` 冇 happens-before）。`published` 標咗 volatile 但冇人讀，等於冇發布。
- **安全發布**：欄位寫完之後，**最後**先賦值 `published`；`loop` 只讀 `published`；Config 發布後不可變，後續改動要重新發布新對象。
- **`stop` 冇 volatile**：JIT 可能把條件提升到暫存器，`loop` 停唔到。改 `volatile boolean stop`。
- **`volatile int seq; seq++` 非原子**：仍然係讀-改-寫三步，多線程會派到同一個號。用 `AtomicInteger`／`LongAdder`，或者鎖。

詳見 [MySQL 主從延遲／讀寫分離](../mysql/replication-lag-read-write-split.md)、[volatile 與 happens-before](../concurrency/volatile-happens-before.md)。

ConsumerRecords recs = consumer.poll(timeout);
