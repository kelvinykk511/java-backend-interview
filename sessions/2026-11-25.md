# 2026-11-25 Java warm-up

## 上次 drill 答案（2026-11-24）

題：下單／查單鏈路同時出現兩件事：

A) 開咗 `spring.threads.virtual.enabled=true` 之後，下單 QPS 幾乎冇升，大量 `HikariPool - Connection is not available, request timed out`。JFR 見到大批 `jdk.VirtualThreadPinned`，熱點係：

```java
public synchronized void checkLimit(String uid) {
    String v = jedis.get("limit:" + uid);
    // ...
}
```

每個請求嘅虛擬線程仲用 `ThreadLocal<byte[]>` 放 1MB buffer「重用」。同事建議「虛擬線程都要池化，用 `ThreadPoolExecutor` core=200 先穩」。

問：點解釋 QPS 冇升、連接池超時、同 pinning？ThreadLocal 同「池化虛擬線程」有咩問題？你會點改（含 JDK 21 vs 24 嘅 pinning 差異）？

B) 表 `orders` 主鍵 `id`，已有 `idx_user_created (user_id, created_at)`。查詢：

`SELECT id, user_id, created_at FROM orders WHERE user_id=? ORDER BY created_at DESC LIMIT 20`

同事話「要再加 `(user_id, created_at, id)` 先算覆蓋，否則一定回表」。另一條 `SELECT id, amount FROM orders WHERE user_id=?` 為咗覆蓋新建咗 `(user_id, id, amount)`，但 EXPLAIN 第一條其實已經 `Using index`，第二條冇用新索引。仲有人用 `INDEX(user_id, created_at(10))` 前綴索引，預期 `SELECT created_at` 都唔使回表。

問：第一條點解已經覆蓋？第二條點解可能用唔到新索引？前綴索引可唔可以覆蓋？`SELECT * WHERE user_id=?` 可唔可以覆蓋？

- **QPS 冇升、Hikari 超時**：開虛擬線程只係讓 Tomcat 接受更多並發；Hikari 連接數冇變。大量虛擬線程一齊 `getConnection`，排隊由 Tomcat 線程池搬去連接池，於是超時。瓶頸喺 DB／下游時，開 VT **唔會**升 QPS。
- **Pinning**：`synchronized checkLimit` 裡面做 `jedis.get()`（阻塞 IO）。JDK 21 持住 monitor 做阻塞 IO 時，虛擬線程**不能 unmount**，carrier 被釘死。JFR `jdk.VirtualThreadPinned` 就係呢個。carrier 數量≈核數，釘滿之後吞吐塌到接近「核數條平台線程」。
- **ThreadLocal 1MB**：虛擬線程係一任務一線程、用完即棄、數量可以極多；每個請求一塊 1MB buffer，堆會按併發線性膨脹，容易 OOM。短生命周期嘅 VT 唔適合做「每線程大緩存」。
- **唔好池化虛擬線程**。用 `ThreadPoolExecutor` core=200 包住 VT，等於人為加返一層併發上限，失去「阻塞即讓出 carrier」嘅好處。要限流就用 `Semaphore`（或等價）對齊下游：Hikari 大小、Redis、簽名機。
- **JDK 21 vs 24**：JEP 491（JDK 24）修咗 `synchronized` pinning，**native／JNI 仍然會釘**。升到 24 之後呢段多數會好轉，但仍然唔好池化、仍然唔好 ThreadLocal 放大對象、仍然要對齊連接池。熱路徑更穩妥係改 `ReentrantLock`，或者唔要鎖住再打 Redis。
- **Boot 開關範圍**：`spring.threads.virtual.enabled` 只換 Tomcat／指定執行器；自己建嘅池、MQ listener 要單獨改。

- **第一條已經覆蓋**。InnoDB 二級索引葉子**已經帶主鍵 `id`**，`(user_id, created_at)` 實際等同 `(user_id, created_at, id)`。查詢要嘅列都在索引裡，而且 `user_id` 等值 + `created_at` 有序，所以已經係 `Using index`，**唔使再加一列 `id`**。
- **第二條唔保證會用 `(user_id, id, amount)`**。把 PK `id` 插喺中間係多餘嘅（本來就會帶上），最左前綴變成 `user_id, id`，對排序或其他條件幫唔到。優化器可能繼續揀更窄、更熱嘅 `(user_id, created_at)` 再回表攞 `amount`。覆蓋索引建咗都要用 `EXPLAIN` 證實；若呢條查詢真係熱，應按查詢把穩定列加喺合適索引嘅尾巴，而唔係亂插 `id`。
- **前綴索引不能覆蓋該列**。`INDEX(user_id, created_at(10))` 只存前綴，交唔出完整 `created_at`，一定要回表。
- **`SELECT *` 幾乎一定回表**，直接殺死覆蓋。
