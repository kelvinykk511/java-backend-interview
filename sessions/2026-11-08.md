# 2026-11-08 Java warm-up

## 上次 drill 答案（2026-11-07）

題：K8s 把同一個 `/actuator/health` 同時當 liveness 同 readiness；某個 Pod 依賴嘅 Redis 抖咗約 2 秒（短暫連唔上）。會發生咩？點拆 liveness／readiness 同業務降級先至唔會重啟風暴？

- **會發生咩**：`/actuator/health` 會彙總所有 `HealthIndicator`（包括 Redis）。Redis 連唔上 → 整體變 `DOWN`。liveness 同 readiness 都打呢個端點 → **兩邊一齊失敗**。
- **Readiness 失敗**：從 Service Endpoints 摘流量（呢步本身合理）。
- **Liveness 失敗**：K8s 當進程已死，**殺 Pod 重啟**。得 2 秒嘅依賴抖，換嚟 JIT／連線池／緩存全部清零，仲可能打斷進行中請求。
- **重啟風暴**：好多 Pod 共用同一個 Redis 就會一齊被殺 → 剩餘實例壓力更大、Redis 恢復更慢 → 滾動重啟循環。`periodSeconds` 短、`failureThreshold` 細時，2 秒已經夠觸發。
- **點拆**：
  - liveness 打 `/actuator/health/liveness`（只反映進程／`livenessState`，**唔好**加 Redis／DB）。
  - readiness 打 `/actuator/health/readiness`；Redis 係關鍵路徑先納入 readiness（摘流量、唔殺 Pod）；只係緩存就唔好綁 readiness，業務用熔斷／降級／回源 DB。
  - Probe 用短超時；indicator 可背景刷新、探針只讀快取，避免每次探都打滿 Redis。
  - K8s `timeoutSeconds`／`failureThreshold` 預留短暫抖動；非關鍵依賴只打 metrics／告警。
- Spring Boot 2.3+ 預設嘅 liveness／readiness **group 唔會自動包晒** Redis 等 indicator；出事通常係「兩個探針都指向彙總嘅 `/actuator/health`」，或者有人把依賴加進 liveness group。

詳見 [Spring Actuator Health](../spring/actuator-health.md)。
