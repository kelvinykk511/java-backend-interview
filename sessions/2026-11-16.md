# 2026-11-16 Java warm-up

## 上次 drill 答案（2026-11-15）

題：下單入口登記咗兩個 Filter + 一個 Interceptor：

1. `SignatureFilter`（普通 `Filter`，唔係 `OncePerRequestFilter`）：用 wrapper 讀 body 驗 HMAC，然後 `chain.doFilter`。
2. `RateLimitFilter`：Redis Lua 令牌桶，key=`rl:{apiKey}`，10 token/s、桶容量 10；Redis 超時時 **fail-open**。
3. `UserInterceptor`：`preHandle` 把 userId 放入 `ThreadLocal`，`afterCompletion` 先 `remove`。

開盤後：(1) 少數「簽名正確」嘅請求偶發驗簽失敗，access log 見到同一個 `requestId` 進咗 Filter 兩次；有啲請求嘅 429 次數好似多扣咗。(2) 一條下單接口回 `DeferredResult`／`CompletableFuture`，另一條喺 Controller 入面 `@Async` 發通知——出現 `UserContext.get()` 為 null，亦有用戶串單。(3) 限流 Redis 一個 slot CPU 100%，同時 Redis 超時率約 5%，撮合被打爆，做市商實際過咗遠超 10/s 的單。

問：(1) Filter 點解跑兩次？點改？(2) ThreadLocal 喺異步下點解會空或串數據，`afterCompletion` 救唔救到？(3) fail-open + 單 key 令牌桶喺開盤點解會失守，你會點改？

- **Filter 跑兩次**：普通 Filter 唔會擋 FORWARD／ERROR／**ASYNC** 二次派發，同一請求會再行成條 Filter 鏈。下單有 `DeferredResult`，ASYNC dispatch 好常見；出錯走 ERROR 亦會再入。`SignatureFilter` 第二次再讀 body，若 wrapper 冇正確複用、或包到已被消耗嘅 stream，HMAC 就會對住空／錯 body 失敗——所以「簽名其實正確」都會偶發驗簽失敗。`RateLimitFilter` 同樣跑兩次 → 同一請求扣兩次 token，429 偏多。
- **點改**：改繼承 `OncePerRequestFilter`（驗簽同扣配額只喺第一次 REQUEST 做，搞清楚 `shouldNotFilterAsyncDispatch`／`shouldNotFilterErrorDispatch`）。Body 用可重讀嘅 `ContentCachingRequestWrapper`，喺最外層包一次。
- **ThreadLocal 會空**：佢只綁定 Tomcat 請求線程。`DeferredResult`／CF 回調、`@Async` 通知跑喺另一條線程，`get()` 自然係 null。
- **會串單**：業務池／`@Async` 池複用線程，若喺 worker 上 set 咗 userId 而唔 `remove`，下一單就看到上一個用戶。`afterCompletion` 只喺 DispatcherServlet 呢條請求鏈被調，**救唔到** `@Async` 線程（個線程根本冇 set，亦唔會幫你清）。上下文放 request attribute／SecurityContext，異步用 TaskDecorator／TTL 顯式傳遞，worker `finally` 一定 `remove`。
- **fail-open + 熱 key 失守**：做市商單一 `rl:{apiKey}` 打同一 Redis Cluster slot → 熱 key，slot CPU 100%。超時約 5% 再 **fail-open**，等於開盤時限流 Redis 一抖就放行，做市商實際遠超 10/s，撮合被打爆。下單路徑要 **fail-closed**（或本地保守令牌桶先擋，Redis 超時唔放行）；熱 key 加本地一層或分片計數；限流 Redis 短超時、隔離、監控 slot CPU。

詳見 [Filter vs Interceptor](../spring/filter-vs-interceptor.md)、[分布式限流](../distributed/rate-limiting.md)。
