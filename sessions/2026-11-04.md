# 2026-11-04 Java warm-up

## 上次 drill 答案（2026-11-03）

題：`orders.user_id` 係 `VARCHAR(32)`、`users.id` 係 `BIGINT`，兩邊都有索引。`WHERE u.id = 10086` 好快，`WHERE u.vip = 1`（幾千個用戶）就好慢。點解？點修？

- **根因係隱式類型轉換**：字串同數字比較，MySQL 會將兩邊轉成數字（double）比。被轉換嘅係 `orders.user_id` 呢一邊 → 等於對索引列套咗函數，**orders.user_id 嘅索引用唔到**做 join 查找。`users.id` 嗰邊冇事（佢係數字列，只係另一邊嘅值被轉）。
- **點解第一句快**：`u.id = 10086` 令 users 變成只有一行嘅常量表，orders 最多只係被掃一輪。
- **點解第二句慢**：幾千個用戶做驅動，每個都要喺 orders 搵 `user_id`，但索引用唔到 → 變成全表掃描 + join buffer（BNL / 8.0.18+ hash join），或者優化器反過來全掃 orders，大表就好慢。
- **點證實**：`EXPLAIN` 見 orders `type=ALL`、`Using join buffer`；`SHOW WARNINGS` 會見到類似 *Cannot use ref access on index ... due to type or collation conversion*。
- **點修**：根治係統一類型（將 `orders.user_id` 改成 `BIGINT`，大表用 [Online DDL](../mysql/online-ddl-large-table.md) / gh-ost）；臨時可以將轉換放喺驅動表一邊：`ON o.user_id = CAST(u.id AS CHAR)`（同時要確認 charset / collation 一致，否則一樣用唔到索引）。
- **額外陷阱**：轉數字比較會令 `'10086abc'`、`'010086'` 都等於 10086，結果都可能錯。

詳見 [MySQL JOIN 算法](../mysql/join-algorithms.md)。
