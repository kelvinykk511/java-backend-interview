# 2026-11-11 Java warm-up

## 上次 drill 答案（2026-11-10）

題：出金服務 Controller 呼叫 `withdrawalService.submitAsync(req)`（`@Async("withdrawExecutor")`），方法入面先寫 DB（`@Transactional`），再組一個只喺方法內用嘅 `SignPayload`（`new` 之後唔 return、唔存欄位），調簽名機，最後發 Kafka。呼叫端用 `future.get(30, SECONDS)` 等結果。池誤用咗默認 `SimpleAsyncTaskExecutor`，而且 `submitAsync` 係同類另一個方法用 `this.submitAsync(...)` 呼叫。高峰：線程數暴漲、Tomcat 池耗盡、偶發「DB 未見提交卻已發 MQ」。請指出至少三個獨立問題，同每個點點改（可提及逃逸分析對 `SignPayload` 分配嘅面試講法）。

- **默認 SimpleAsyncTaskExecutor**：`@Async` 若走到代理但冇配好名為 `withdrawExecutor` 嘅池，會用 `SimpleAsyncTaskExecutor`——每任務一條新線程、無上界、唔重用 → 高峰線程數暴漲。改：顯式配有界 `ThreadPoolTaskExecutor`（core／max／queue／拒絕策略），Bean 名對得上。
- **`this.submitAsync(...)` 自調用**：`@Async` 靠 Spring 代理；`this` 繞過代理 → 註解失效，方法喺呼叫線程同步跑。Controller 注入代理嘅路徑仍然可以 async；同類內部呼叫就唔會。改：抽到另一 Bean、注入自身、或（較醜）`AopContext.currentProxy()`。
- **`future.get(30s)` 堵 Tomcat**：就算 async 生效，HTTP 線程仍卡住等簽名／Kafka，高峰 Tomcat 池耗盡，同「異步」目的相反。改：要同步就唔好假裝 `@Async`；要異步就立即 202 + 查詢／回調，唔好喺請求線程 `.get()`。
- **事務未 commit 就發 MQ**：`@Transactional` 喺方法結束先提交；Kafka 喺方法內、commit 前已發出。消費者可能讀唔到行，或方法稍後回滾但消息已出。改：`afterCommit` 再發，或 Transactional Outbox。
- **SignPayload 同逃逸分析**：若對象真係方法內新建、唔 return、唔存欄位，而且簽名呼叫被 JIT 證明唔讓佢逃逸，可以 NoEscape → 標量替換、唔一定進堆。一傳入簽名客戶端／RPC／日誌就好易 ArgEscape／GlobalEscape。呢個只係效能加分，**唔好當正確性假設**。
