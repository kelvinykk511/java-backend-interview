# 2026-11-10 Java warm-up

## 上次 drill 答案（2026-11-09）

題：滾動發佈開咗 `server.shutdown=graceful`、`spring.lifecycle.timeout-per-shutdown-phase=30s`、`terminationGracePeriodSeconds=30`、`preStop sleep 15`。發佈期間 LB 偶發 502，而且約 20s 嘅在途請求被截斷。呢三個時間數字點算錯？你會點改？另外，若停機當下 Kafka 剛拉到一筆出金消息仲喺調簽名機，被 SIGKILL 截斷後靠咩保證唔重複出金？

- **時間點算錯**：口訣係 `preStop + lifecycle 等待 < terminationGracePeriodSeconds`（仲要留 JVM 收尾緩衝）。呢度 `15 + 30 = 45 > 30` → Spring 仲喺等在途／停 MQ，K8s 已經 **SIGKILL**。約 20s 請求被截斷係預期結果，唔係「graceful 壞咗」。
- **502**：SIGTERM 同從 Endpoints 摘流量**並行**。`preStop sleep` 本嚟用嚟等摘流量，但總預算唔夠時，一邊未摘乾淨、一邊進程已被殺或已停收 → LB 見到 connection reset／502。
- **點改**：
  1. 拉高 `terminationGracePeriodSeconds`（例如 60–90），令 `preStop + lifecycle + 緩衝 < grace`；或縮短 lifecycle／preStop，但要覆蓋真實在途 P99。
  2. 停機時 readiness 先變不可用；確認入口係 `exec java`，SIGTERM 真係打到 JVM。
  3. 長任務（簽名／鏈上）唔好假設一定喺 grace 內做完 → 外置狀態機／可續跑。
- **SIGKILL 後唔重複出金**：Kafka 係至少一次，重平衡會再投遞。靠**業務冪等**：出金單號／冪等鍵做唯一約束；狀態機（created → signing → submitted → confirmed）；未上鏈成功唔標完成；重試只對「可安全重放」狀態；簽名／廣播要可查詢去重。優雅停機減少重複，**冪等先係正確性**。

詳見 [Spring Boot 優雅停機](../spring/graceful-shutdown.md)。
