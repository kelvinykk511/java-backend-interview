## 上次 drill 答案（2026-11-22）

題：對帳／下單鏈路同時出現兩件事：

A) 千萬級 `orders` 要加可空列 `risk_tag`。有人喺主庫直接跑冇寫 `ALGORITHM` 嘅 `ALTER TABLE ... ADD COLUMN`。同時午夜對帳事務掃咗呢張表 25 分鐘未 commit。線上湧現 `Waiting for table metadata lock`，從庫延遲急升。同事話「8.0 加列一定 INSTANT，唔會鎖；如果驚就改 pt-osc，有觸發器更穩」。

B) 下單去重用進程內 `ConcurrentHashMap<String, OrderCtx>`：`if (!map.containsKey(oid)) { map.put(oid, ctx); place(); }`。高峰偶發同一 `oid` 下了兩次。另一條補償路徑用 `computeIfAbsent(oid, k -> { map.put(relatedId, ctx); return ctx; })`，偶發線程卡住。呢個 map 無淘汰、無上限，服務跑一週堆內存一直升。

問：(1) 點解可能唔係 INSTANT？MDL 排隊鏈點形成？pt-osc「更穩」啱唔啱？你會點改 DDL，同點處理呢個長事務？(2) 點解會重複下單？`computeIfAbsent` 點解可能卡住？內存你會點改？CHM 適唔適合做跨實例去重？

- **8.0 加列唔等於一定 INSTANT**。唔寫 `ALGORITHM=INSTANT`，一旦 Instant 用唔到（8.0.29 之前喺中間插列、`ROW_FORMAT=COMPRESSED`、FULLTEXT、已達 64 個 row version、同一次 ALTER 夾咗唔支援 Instant 嘅操作、加 AUTO_INCREMENT 列等），MySQL 可能**默默改走 INPLACE／COPY 重建**，主庫 IO、從庫延遲一齊爆。生產要顯式指定，唔支援就立即報錯再改方案。
- **MDL 排隊鏈**：對帳 25 分鐘未 commit，持住表嘅共享 MDL。任何 DDL（包括 INSTANT）都要排他 MDL，於是卡住；之後新嚟嘅查詢／DML 要等呢把排他鎖，會**再排喺 DDL 後面**，整張表 `Waiting for table metadata lock`。INSTANT 只係搶到鎖之後好快，搶鎖之前一樣可以卡死業務。
- **先結束或殺掉呢條長事務**，唔好只殺等緊嘅 DDL（殺咗，下一次仲會撞同一把鎖）。低峰執行，並設合理 `lock_wait_timeout`。
- **pt-osc「有觸發器更穩」唔啱**。觸發器令每個寫都多一次維護，忙表通常 **gh-ost** 更合適。工具 cut-over 仍然要短暫 MDL，代替唔到「先清長事務」。
- **`containsKey` + `put` 非原子**。兩個線程可以同時見到冇呢個 `oid`，兩邊都 `place()`。應用 `putIfAbsent`／`computeIfAbsent` 只解決**單進程**；跨實例必須靠 DB 對 `oid` 嘅唯一約束／狀態機。
- **`computeIfAbsent` 入面再 `map.put(relatedId, ...)`**：持住當前桶鎖時又改同一張 map，可能卡死或丟 `IllegalStateException`。mapping function 唔好再變更呢個 map。
- **無淘汰、無上限**：當去重表會撑爆堆。用有 size／TTL 嘅本地緩存（例如 Caffeine），或根本唔用進程內 map 做去重。
- **進程內 CHM ≠ 跨實例冪等**。
