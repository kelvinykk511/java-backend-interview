# 2026-11-18 Java warm-up

## 上次 drill 答案（2026-11-17）

題：下單接口 SLA 1s，同步調風控 HTTP：

- WebClient：connect 200ms、`responseTimeout` 2s；超時後再自動重試 3 次（每次都係新請求），之間無退避。
- 未設 pool acquire 超時；風控同「查行情」共用同一個 Resilience4j `CircuitBreaker` name。
- 之後補上熔斷：`slowCallDurationThreshold=200ms`、`slowCallRateThreshold=50%`，`permittedNumberOfCallsInHalfOpenState=50`。OPEN 時 fallback 係「再打一次備援風控 URL」，DNS 其實指向同一個集群 VIP。

風控故障期間掛住唔回：Tomcat 工作線程很快耗盡，風控入口 QPS 變成平時約 4 倍。閘打開後，行情一抖，下單亦大量 fail-fast；HALF_OPEN 期間風控又被打到差唔多滿載。

問：(1) 點解流量大約變 4 倍、Tomcat 會被打滿？超時、重試同取連線你會點改？(2) 共用 breaker name、呢個 fallback、HALF_OPEN=50 各有咩問題？Retry 同 CircuitBreaker 你會點包？

- **4 倍流量 + Tomcat 被打滿**：`responseTimeout` 2s 已經長過 SLA 1s，單次呼叫都可以比用戶預算更長。超時後再自動重試 3 次（無退避）= 1 次原請求 + 3 次重試，最多打下游 **4 次** → 風控掛住唔回時入口 QPS ≈ 4 倍（retry storm）。每次嘗試最長約 2s，串行最多約 8s 佔住一條 Tomcat 線程。未設 pool acquire 超時，池耗盡時線程仲會無限卡喺借連線，耗盡更快。
- **點改超時／重試／取連線**：預算對齊 SLA（總時長 < 1s；connect 可留 100–200ms，responseTimeout 要預留自己處理時間，例如 300–400ms）；設短嘅 pool acquire 超時；重試要看**剩餘預算**、次數要少、加指數退避。下單調風控唔好盲目重試。光有超時唔夠，要配熔斷，避免繼續用線程「等死」。
- **共用 breaker name**：風控同查行情共用一個滑動窗口，風控一故障就 OPEN，行情一抖（或之後任何失敗）下單亦被 fail-fast（連坐）。應按下游、按接口分開。
- **Fallback 打備援 URL，但 DNS 指向同一個集群 VIP**：等於繼續打已病嘅同一批機器，降級無效仲加流量。Fallback 應係明確失敗、短 TTL 緩存（讀場景），或真正獨立嘅備援。下單禁止假成功。
- **HALF_OPEN=50**：一開閘就放 50 個探針，下游未恢復就被再打滿、立刻又 OPEN。探針要少（幾個），成功再逐步放行。
- **包法**：用 `Retry(CircuitBreaker(call))`——每次嘗試都計入熔斷；一旦 OPEN，重試都會 fail-fast，唔再打下游。若 `CircuitBreaker(Retry(call))`，要等內部成串重試走完先當一次結果，開閘慢、線程佔更久、下游被打更狠。業務 4xx／「餘額不足」唔好計入失敗，亦唔好重試。
