## 上次 drill 答案（2026-11-27）

題：入帳／下單同時出現兩件事：

A) Kafka group `credit`，`enable.auto.commit=false`，`max.poll.records=50`。代碼大致係：

```java
ConsumerRecords recs = consumer.poll(timeout);
for (ConsumerRecord rec : recs) {
  pool.submit(() -> credit(rec)); // 異步，唔等完成
}
// 即刻提交呢批「見到嘅最大 offset」
consumer.commitAsync(offsetOfLastRecordInBatch);
```

`ConsumerRebalanceListener` 係空嘅。某次 worker 入帳慢，發版 rebalance 之後另一個 consumer 又 poll 到同一批，但舊 worker 之後先寫完 DB。同時有一條 record 入帳失敗——因為 max offset 已 commit，呢條以後再亦唔會被同 group 拉到。有人修咗「改回自動提交」，但主線程把 record 丟去線程池之後仍然即刻 `poll()`。

問：點解會**重複入帳**同**「丟失」（offset 超前）**同時出現？線程池 + 提交最大 offset 有咩問題？自動提交咁改會唔會更穩？你會點改提交時機、併發同 rebalance？自己組 offset map 時 `record.offset()` 同 `offset() + 1` 有咩分別？

B) 下單 API：`Idempotency-Key` 只放 Redis（`SET NX EX 30s`），成功後**先扣款**，再異步把最終 response 寫入 Redis（多數時候只存咗 `1`，冇訂單號）。`client_oid` 只有應用層 `SELECT` 再 `INSERT`，冇唯一索引。用戶網路超時 3 秒就用同一 key 重試；亦有人超時之後**換一個新 key** 再提交（同一個 `client_oid`）。第一次實際 8 秒先扣完款。出現：重複扣款、第二次拿到「重複／處理中」但其實錢已扣、或者兩張訂單。

問：30s TTL、先扣後寫 response、只存 `1`、換 key 重試，各有咩問題？`Idempotency-Key` 同 `client_oid` 要點一齊用？進行中嘅請求你會點處理？

- **重複同「丟失」可以同時出現**。主線程 poll 完就丟去線程池，即刻 `commitAsync` 呢批**最大 offset**。Kafka 認為呢批已完成，但 worker 可能未寫完，甚至中間有一條失敗。失敗嗰條被「帶埋交」→ 同 group 唔會再拉到 → 表面丟失，其實係 **offset 超前**。
- **`commitAsync` 係異步**，發版 rebalance 時 listener 又係空：唔會等 worker，亦唔會 `commitSync` 已完成嘅水位。若提交尚未成功／未可見，新 consumer 從舊 committed offset 再 poll 同一批；舊 worker 之後又寫完 DB → **重複入帳**。同一批入面，失敗記錄被 max offset 交走（丟），未提交完成又遇上 rebalance（重複），兩者可以一齊出現。
- **線程池 + 交最大 offset** 嘅核心問題：交嘅係「見到嘅位置」，而唔係「由細到大連續處理完成嘅水位」。中間有洞都會被當成完成。
- **改回自動提交更唔穩**。auto-commit 喺下次 `poll()`（或 interval）交上一批；主線程即刻再 poll，worker 未完就交，同樣會超前。rebalance 仍然冇 listener。
- **點改**：先處理再 `commitSync`。要併發就按 **partition 單線程**，只交連續 watermark，唔好交 max。`onPartitionsRevoked` 要停／等呢啲 partition 嘅 worker，再 `commitSync` 水位；舊任務唔好再寫（入帳本身要用唯一鍵做冪等）。`max.poll.interval.ms` 要蓋過處理時間，或者 pause 再處理。
- **自己組 offset map 要交 `record.offset() + 1`**。Kafka 記嘅係「下一條要讀嘅 offset」。交 `offset()` 會令呢條再被拉一次。

- **30s TTL**：第一次 8 秒先扣完；key 一過期，重試會再扣。Redis 短 TTL 唔可以當真相，要比重試窗口長，而且最終以 DB 為準。
- **先扣後異步寫 response**：中間重試可能見到「處理中」但其實錢已扣；若 key 已過期或換咗新 key，就會再扣。扣款同落單記錄要**同一事務**寫完。
- **只存 `1`**：重試還原唔到原訂單號／response，前端以為失敗。要存狀態（PROCESSING / SUCCEEDED / FAILED）同完整 response。
- **換 key 重試同一個 `client_oid`**：新 Idempotency-Key 令 SET NX 成功，當成新請求 → 雙扣／兩張單。
- **一齊用**：`client_oid`（業務唯一鍵）加 **DB 唯一索引** 先係真相；Idempotency-Key 用嚟回放同一請求嘅 response。同一個 `client_oid` 換 key 都應返回同一張單（payload 衝突先 409）。唔好只靠應用層 SELECT 再 INSERT。
- **進行中**：寫 PROCESSING，同樣 key 重試返回 409／「稍後用同一 key 再查」，**唔好再扣**，亦唔好當成功。PROCESSING 可設超時回收，但重試仍要撞同一條業務唯一鍵。

詳見 [Kafka Consumer Group、Offset 提交](../kafka-mq/consumer-group-offset-delivery.md)、[Idempotency-Key 同業務唯一鍵](../distributed/idempotency.md)。

出金／限額同時出現兩件事：

A) 出金服務：

```java
@Service
public class WithdrawService {
  @Autowired WithdrawService self; // 打算用代理

  @Transactional
  public void withdraw(Cmd cmd) {
    debit(cmd);              // 同類直接調
    self.notifyRisk(cmd);    // 想異步通知
  }

  @DistributedLock(key = "#cmd.uid")  // 自定義切面，Order 用預設，比事務更內
  public void debit(Cmd cmd) { /* 扣凍結、寫出金單 */ }

  @Async
  @Transactional
  public void notifyRisk(Cmd cmd) {
    riskLogRepo.save(...);   // 同一張單再插一條風控日誌
    mq.send(cmd);            // 發出去給風控消費端
  }
}
```

有人覺得 API 唔應被 DB 拖住，打算把 `@Async` 一齊標喺 `withdraw` 上。另外 Kotlin 重寫咗 `debit`，方法唔係 `open`。高併發下偶發超賣／重複扣；風控消費端有時查唔到剛寫嘅日誌；有時出金成功但鎖明顯冇生效。

問：`debit` 條鎖同事務實際會唔會生效？`@Order` 反咗有咩後果？`@Async` 標喺 `withdraw` 同標喺 `notifyRisk` 分別會點？MQ 應該幾時發？你會點拆方法同切面順序？

B) 限額熱數據放 Redis。主庫為咗延遲設咗 `save ""`、`appendonly no`，只喺從庫開 AOF；systemd 自動重啟。之後磁碟滿，有節點出現 `MISCONF ... unable to persist to disk`，有人把 `stop-writes-on-bgsave-error` 改成 `no`，再加 `no-appendfsync-on-rewrite yes`「減少搶盤」。某晚主庫被 OOM kill，自動用空數據集起來，所有從庫數據都冇咗。團隊以為「從庫有 AOF，主庫唔持久化冇問題」。

問：點解從庫 AOF 救唔到？`MISCONF` 同把 `stop-writes-on-bgsave-error` 改 `no` 各意味住咩？`no-appendfsync-on-rewrite yes` 會加大邊段丟數據窗口？主從持久化同自動重啟你會點配？限額／賬本你會唔會只靠 Redis 持久化？
