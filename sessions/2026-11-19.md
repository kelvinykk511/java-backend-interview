# 2026-11-19 Java warm-up

## 上次 drill 答案（2026-11-18）

題：出金服務同時出現兩件事：

A) 業務事務：`SELECT * FROM withdraw_order WHERE uid=? AND status='PENDING' FOR UPDATE`（二級索引 `(uid, status)`），再按主鍵把狀態改成 `PROCESSING`。對帳任務按主鍵批量 `UPDATE withdraw_order SET status='EXPIRED' WHERE id IN (...)`，修正錯單時偶爾仲會改 `uid`。隔離級別 RR。併發一高就偶發 1213。

B) 為咗熱更新風控規則，每分鐘 `new URLClassLoader(jar)` 載入規則包。介面 `RiskRule` 喺應用 classpath，但規則 jar 裡面又 shade 多一份 `RiskRule`。上線後偶發 `ClassCastException: com.foo.RiskRule cannot be cast to com.foo.RiskRule`；跑一日，Metaspace 同 loaded classes 持續上升。規則執行完，loader 被放進一個靜態 `Map<String, ClassLoader>` 方便「下次重用」。

問：(1) 點解 A 會死鎖？`INNODB STATUS` 你會對住邊啲欄證實（index 名、HOLDS／WAITING）？加鎖同 SQL 你會點改？改 RC 係咪就唔會死？(2) 點解會 CCE？點解 Metaspace 會爬？類加載同卸載你會點改？

- **點解 A 會死鎖**：InnoDB 行鎖掛喺**索引記錄**上。業務走 `(uid, status)`，通常**先鎖二級索引**，再回表鎖 **PRIMARY**。對帳 `WHERE id IN (...)` **先鎖主鍵**；`status`（有時連 `uid`）都喺二級索引上，UPDATE 要維護索引，再去鎖／刪舊、插新二級記錄。時序一對上：A 持有二級、等 PRIMARY；B 持有 PRIMARY、等二級 → 環等待 → 1213。如果對帳只改非索引列，多數只係 1205 等主鍵行鎖，而唔係死鎖；呢題會死，正正因為改咗索引列。
- **點證實**：`SHOW ENGINE INNODB STATUS\G` → `LATEST DETECTED DEADLOCK`（只留最近一次）。兩邊對住 **HOLDS**／**WAITING**、**index 名**（`PRIMARY` vs `(uid, status)` 嗰條）、`lock_mode`（X、`rec but not gap` 等）。`WE ROLL BACK TRANSACTION (n)` 係 undo 較細嗰邊。長期開 `innodb_print_all_deadlocks=ON`；8.0 用 `performance_schema.data_locks` 睇**當前**等待（死鎖回滾後現場可能已散）。
- **點改**：兩邊都走**同一條加鎖路徑**——先按主鍵集合 `SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE`，再更新；跨用戶就按 `uid`／`id` 由細到大排完先鎖。`WHERE` 走索引，事務要短，唔好喺事務入面做 HTTP。應用對 1213 做有限次、**成個事務從頭**重試（唔好只重跑報錯嗰條 SQL）。少改 `uid` 呢類索引列。
- **改 RC 救唔到**：呢個係已有行上嘅行鎖互等，唔係 gap lock。RC 減少 gap，但救唔到「二級 ↔ 主鍵」加鎖順序相反。
- **點解 CCE**：類嘅唯一性 = 全限定名 + ClassLoader。應用 classpath 一份 `RiskRule`（父／應用 loader），jar 又 shade 多一份，由子 `URLClassLoader` 再 `defineClass`，JVM 裡係**兩個唔同嘅類**。cast 就會出現 `com.foo.RiskRule cannot be cast to com.foo.RiskRule`。介面必須只由父 loader 載，插件 jar **唔好再打包**同名介面，子 loader 只載實作。
- **點解 Metaspace 會爬**：每分鐘 `new URLClassLoader`，再用靜態 `Map` 持有 loader，舊 loader 同佢載入嘅類**斷唔到引用、卸唔掉**。就算名義上「重用」，key 若按版本／時間累積，就單調上升。調大 `MaxMetaspaceSize` 只係延後。點改：介面唔 shade；每個版本只留一個 loader，舊版要從 Map **移除**，並 `close()` `URLClassLoader`，確認冇靜態集合、線程池 ThreadLocal、日誌 appender 再引用；先證實 loaded classes 會回落，先再定期熱更新。

## 今日 drill

下單鏈路同時出現兩件事：

A) 調風控用 Apache HttpClient。服務端 keep-alive timeout 30s，客戶端關咗取出驗證、idle timeout 設 60s；有個攔截器讀完 response headers 就 return，body 喺異常路徑經常冇 consume。另外每個請求 `HttpClients.createDefault()`。高峰期池看起來耗盡，大量請求卡在借連線，偶發 `NoHttpResponseException`，本機仲見到好多次完整 TLS 握手。有人建議把池同 Tomcat 線程各加一倍，並且對所有 reset 自動重試 3 次（包括下單）。

B) 用戶持倉用一個 Hash `pos:{uid}`，活躍做市商可以有幾萬個 field。對帳任務 `HGETALL pos:{uid}` 之後 `DEL pos:{uid}` 再重建；過期同覆蓋寫亦用 `DEL`。開盤時呢個 Redis 節點 RT 飆高、replica 落後，Cluster 入面就呢個 node 內存特別高。有人話「呢個係 hot key，加一層本地 Caffeine 就得」。

問：(1) A 裡面邊啲做法令 Keep-Alive 失效、連線洩漏、偶發 reset？池同線程、重試你會點改？(2) B 係 big key、hot key，定兩者都有？點解本地緩存救唔到 `DEL`？定位同拆／刪你會點改？
