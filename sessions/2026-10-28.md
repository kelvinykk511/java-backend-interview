## 上次 drill 答案（2026-10-27）

題：入帳服務用 `@RetryableTopic`（3 個 retry topic + DLT），key = userId。用戶 A 嘅 event1（入帳 +100）失敗入咗 retry，event2（扣款 −50）緊接成功處理。會出咩問題？點改先保證同一用戶嘅事件順序？

- **問題**：retry topic 係**非阻塞**重試，event1 被搬走，同 partition 後面嘅 event2 照常消費 → 同一用戶**先扣後入**。餘額可能變負 / 扣款被拒，event1 之後重試成功又再入帳，結果同真實順序唔一致；帳本對唔上。
- **改法 1：阻塞重試**：對講順序嘅 topic 唔用 retry topic，用 `DefaultErrorHandler` + 退避原地重試（失敗就唔提交 offset，整個 partition 停住），總時長要短過 `max.poll.interval.ms`；長時間就 `pause/resume` partition。代價：一條壞消息卡住成個 partition。
- **改法 2：按 key 停泊（park）**：一個 userId 有事件入咗 retry，就記低「呢個 key 已停泊」；之後同 key 嘅事件**全部跟住排隊**入同一個停泊隊列，按序重放，其他用戶照行。
- **兜底**：每個用戶事件帶**遞增序號 / version**，帳本只接受 `seq = last + 1`，亂序就拒絕或等；加上冪等鍵防重複入帳。
