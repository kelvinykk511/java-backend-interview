# 2026-10-30 Java warm-up

## 上次 drill 答案（2026-10-29）

題：對帳服務喺 Tomcat 請求線程入面用 `parallelStream()` 逐個調 `walletClient.queryBalance`（每次約 200ms），一上量另一個用 `CompletableFuture.supplyAsync(...)`（冇傳 executor）嘅推送功能都變慢。點解？traceId 有咩異常？點改？

- **點解一齊慢**：`parallelStream` 同冇傳 executor 嘅 `supplyAsync` 都用 **`ForkJoinPool.commonPool()`**，全 JVM 共用，worker 數只有「CPU 核數 − 1」。阻塞 HTTP 調用霸住 worker 200ms，請求一多 commonPool 被塞爆，推送任務只能排隊。
- **traceId 異常**：MDC 係 ThreadLocal，唔會傳去 commonPool worker → 部分日誌 **traceId 空**，或者見到**上一個任務殘留嘅 traceId**（串號）；而調用線程自己都會參與執行，所以同一請求一半 log 有 traceId、一半冇。
- **點改**：
  - I/O 唔好用 `parallelStream`；改用**專用、有界**線程池 + `CompletableFuture.supplyAsync(task, walletExecutor)`，加 `orTimeout` 同整體超時。
  - 更好：錢包服務提供**批量查詢**接口，一次查一批 userId。
  - MDC 用包裝（拷貝 MDC 入任務、`finally` 清走）或 `TaskDecorator` 傳遞。
  - JDK 21 可用虛擬線程 + `Semaphore` 限制併發，保護下游。
  - 推送功能都應該傳自己嘅 executor，唔好同人共用 commonPool。
