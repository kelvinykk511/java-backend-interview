# 2026-11-17 Java warm-up

## 上次 drill 答案（2026-11-16）

題：入帳服務兩個做法同時出現過：

A) Spring MVC + worker 池：`XREADGROUP GROUP credit worker-${pid} STREAMS deposits > BLOCK 2000`，入帳成功後先 `XACK`。每次發版／重啟，consumer name 都會變（帶咗 pid）。

B) 有人把消費改到 WebFlux 進程，喺 `reactor-http-nio` Event Loop 上對 Redis 做阻塞式 `XREADGROUP`，入帳仍用同步 JDBC，用 `.block()` 等寫庫完成再 `XACK`。

發版後：部分充值一直停在 PEL，新消息仲讀到；同時呢個 WebFlux 進程嘅健康檢查同其他非阻塞接口偶爾一齊卡死。

問：(1) `worker-${pid}` + 只讀 `>` 點解會令舊消息無人認領？你會點改 consumer name 同恢復流程？(2) 喺 Event Loop 上阻塞 `XREADGROUP` 再 `.block()` 等 JDBC，會點樣拖垮服務？線程模型同 ACK 時機你會點選？

- **舊消息無人認領**：`>` 只讀「從未投遞過」嘅新消息。已投遞未 ACK 嘅會留喺**該 consumer** 嘅 PEL。`worker-${pid}` 每次重啟都係一條**新** consumer，舊 PEL 仍然掛喺已死嘅舊名下面。新進程只讀 `>`，又冇用舊名從 `0-0` 撈 pending，亦冇 `XCLAIM`／`XAUTOCLAIM`，所以新充值仲讀到，發版前未 ACK 嘅就一直卡住。
- **點改**：consumer name 要穩定（配置嘅實例名／`credit-0`，唔好帶會變嘅 pid）。啟動先處理自己 PEL（`XREADGROUP … 0-0`），並對死 consumer 做 `XPENDING` + `XCLAIM`／定期 `XAUTOCLAIM`（設 min-idle-time）。`XGROUP DELCONSUMER` 之前確認 PEL 已空。入帳用 `depositId` 冪等，因為呢條路徑係至少一次。
- **Event Loop 被堵**：`reactor-http-nio` 就係少量 Event Loop。阻塞 `XREADGROUP BLOCK 2000` 再 `.block()` 等 JDBC，等於把 loop 線程佔死。健康檢查同其他非阻塞接口都行呢批線程，所以會一齊卡死。呢個唔係 Redis 壞，係線程模型用錯。
- **點選**：阻塞式 Redis + JDBC 應該放喺 MVC + 專用 worker 池（做法 A，但要改穩定 consumer name）。若留喺 WebFlux，要用 reactive Redis，JDBC 丟去 `boundedElastic`／專用池，**禁止**喺 Event Loop 上 `.block()`。ACK 一定要喺入帳成功（DB commit）之後先做；先 ACK 再崩潰會丟消息。失敗就留喺 PEL，靠冪等重放。

詳見 [Spring MVC vs WebFlux 線程模型](../spring/mvc-vs-webflux-thread-model.md)、[Redis Stream：XREADGROUP 與 PEL](../redis/stream-xreadgroup-pel.md)。
