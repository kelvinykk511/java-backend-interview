# 2026-11-06 Java warm-up

## 上次 drill 答案（2026-11-05）

題：G1 服務每次導出報表（一次過 `readAllBytes` 一個 20MB 文件），GC log 頻繁出現 `G1 Humongous Allocation`，有時仲有 `to-space exhausted`。`G1HeapRegionSize` 係 4MB。點解 20MB 對象對 G1 特別傷？除咗加大 heap，你會點改？

- **Humongous 定義**：對象大小 **> RegionSize / 2**。Region = 4MB → **> 2MB** 就算 Humongous。20MB 要佔 `ceil(20/4) = 5` 個**連續** Region。
- **點解傷**：Humongous 直接佔 **Old 性質** Region，Young GC 基本搬唔走／壓縮差 → **碎片**；連續空 Region 唔夠就 allocation failure，嚴重時 Full GC；evacuate 期間 **to-space exhausted** 好常見。
- **重要陷阱**：`G1HeapRegionSize` **最大 32MB**，半區 = 16MB → **超過 16MB 嘅對象永遠係 Humongous**。單靠加大 RegionSize **救唔到 20MB**。
- **改法（根治）**：唔好 `readAllBytes`；改**流式／分塊**（`InputStream` + 固定 buffer、`Files.newInputStream`、分頁讀）；報表邊讀邊寫／邊壓縮；避免一次性大 `byte[]`／大 `List`；必要時 off-heap 或落盤。加大 heap 只係緩和，**根治係唔造大對象**。

詳見 [對象分配：TLAB / Humongous](../jvm/object-allocation-tlab.md)。
