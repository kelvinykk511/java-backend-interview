# 2026-11-22 Java warm-up

## 上次 drill 答案（2026-11-21）

題：出金鏈路同時出現兩件事：

A) 出金服務用 Redisson 鎖 `withdraw:{wid}`，為咗「唔好鎖太耐」指定 `leaseTime=3s`。臨界區入面先打風控 HTTP（P99 有時 4s）再寫 DB。有人話 watchdog 會自動續期。一次 GC 停頓約 2s 之後，兩台實例都寫成功，出現重複出金。另外 Redis 主從，鎖寫咗未複製就 failover，亦出現過兩把鎖。有人建議改用 RedLock，並且把 TTL 設成永不過期。

B) 出金狀態更新同 `kafkaTemplate.send` 寫喺同一個 `@Transactional`。後來改用 outbox，但 outbox `INSERT` 單獨標咗 `REQUIRES_NEW`，「業務失敗都要留痕」；Relay 用 `SELECT * FROM outbox WHERE status='NEW' LIMIT 100`（無索引），send 成功先改 SENT，進程喺 send 成功、標記前崩潰就會重發。下游收到訊息就扣凍結、打款，冇用 `withdrawId` 唯一鍵。

問：(1) 點解 watchdog 冇救到？leaseTime、GC、臨界區做 RPC、主從 failover、RedLock 同永不過期，你會點改？鎖同正確性邊界係乜？(2) 事務內直接 send、同 outbox 用 `REQUIRES_NEW`，各有咩問題？Relay 掃描／標記同下游你會點改，先算 Outbox 用對？

- **指定 `leaseTime=3s` 就唔會開 watchdog**。Redisson 只有「唔指定租約、由 watchdog 續期」（預設約 30s，大約每 1/3 續一次）先會自動續。硬 TTL 3s，臨界區先打風控 HTTP（P99 4s）一定會過期，第二台攞到鎖，兩邊都寫成功。
- **GC 停頓約 2s** 令呢個窗口更大：續期心跳停、或者租約已掉之後原持有者醒返繼續寫。就算開咗 watchdog，STW 長過續期週期一樣會丟鎖。Watchdog 只表示「持鎖線程仲活就續期」，**唔係**正確性保證，更擋唔到 failover。
- **臨界區唔好做 RPC**。鎖只保護好短嘅狀態更新。出金正確性靠 `withdrawId` 唯一鍵／狀態機（例如 `FROZEN → PAYING → PAID`），必要時寫庫帶 fencing token（版本號）。Redis 鎖只係減併發，唔可以當唯一防線。
- **主從未複製就切主**：新主冇呢把鎖，變成雙持有。Redis 複製預設異步，呢個係已知缺口，唔係偶發 bug。
- **RedLock 有爭議**（時鐘／進程暫停假設），仍然冇 fencing，出金唔好靠佢。TTL 永不過期更差：進程崩潰就死鎖，要人手解，一樣冇 fencing。
- **事務內 `kafkaTemplate.send` 唔入 DB 事務**。commit 前已發出：下游可能見到未提交、甚至之後被 rollback 嘅出金；commit 後先發，進程掛／發送失敗又會丟。`AFTER_COMMIT` 都唔係 Outbox。
- **Outbox `INSERT` 用 `REQUIRES_NEW`**：業務失敗／rollback，打款事件已經獨立提交，Relay 會當成功出金去打款。「留痕」應該用審計表，唔好同出金事件混。業務更新同 outbox 必須同一 `REQUIRED` 事務。
- **Relay `SELECT * ... WHERE status='NEW' LIMIT 100` 無索引**：表大就全表掃，多實例會搶同一批。要 `(status, id)` 之類索引，`FOR UPDATE SKIP LOCKED`，或改 CDC。
- **先 send 再標 SENT、中間崩潰會重發**：呢個係 at-least-once，做法啱嘅前提係下游冪等；**唔好**先標 SENT 再 send（會丟消息）。下游必須用 `withdrawId` 唯一約束／合法狀態轉移，否則重發就重複打款。呢個先算 Outbox 用對。
