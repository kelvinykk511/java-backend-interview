# 三色標記 + 並發標記漏標（SATB vs 增量更新）

> 面試問法：「G1 / CMS 並發標記時，用戶線程仲喺度改引用，點樣保證唔會將活對象當垃圾清走？」

## 一句講晒
並發標記用「三色」記錄進度；用戶線程同時改引用可能令**活對象漏標**。修法係用**寫屏障**記低改動：CMS 用**增量更新**，G1 用 **SATB（開始時快照）**，最後一個短 STW（remark）補返。

## 三色係咩
- **白**：未掃到（標記完仲係白 = 垃圾）
- **灰**：自己掃到，但佢引用嘅對象未掃完
- **黑**：自己同所有直接引用都掃完

## 漏標要同時滿足兩個條件
1. 用戶線程將一個**白對象**掛到**黑對象**下面（黑唔會再被掃）
2. 同時刪咗所有**灰對象 → 該白對象**嘅路徑

兩個同時發生 → 白對象明明仲有人用，但冇人再掃到佢 → 被當垃圾回收 → 程序出錯（唔係慢，係錯）。

## 兩種修法：各破一個條件
| | 增量更新（Incremental Update） | SATB（Snapshot-At-The-Beginning） |
|---|---|---|
| 誰用 | CMS | G1（Shenandoah 都係 SATB 一類） |
| 破哪個條件 | 條件 1：黑對象新增引用 → 將黑重新變灰，remark 再掃 | 條件 2：刪引用前，將**舊值**記低當活 |
| 屏障位置 | 寫後屏障（記新值） | 寫前屏障（記舊值） |
| 代價 | remark 要重掃變灰嘅對象，可能好耐 | 會有**浮動垃圾**（本輪死咗都當活，下輪先清），但 remark 短 |

- 新分配嘅對象：G1 用 TAMS（Top At Mark Start）指針，標記開始之後分配嘅一律當活。

## 常見追問 / 陷阱
- **「多標」同「漏標」唔同**：多標 = 浮動垃圾，只係晚啲清，冇害；漏標 = 錯殺活對象，係正確性 bug，所以一定要防。
- **點解仲要 STW？** 初始標記（GC Roots）同 remark（處理 SATB 隊列 / 重掃）都要短暫停頓；並發階段先唔停。
- **ZGC 呢？** 用**讀屏障 + 染色指針**，連移動對象都並發做，思路唔同（見 [zgc-vs-g1](zgc-vs-g1.md)）。
- 寫屏障唔係內存屏障（volatile 嗰種）；呢度係 GC 喺每次寫引用時插入嘅一小段代碼。
