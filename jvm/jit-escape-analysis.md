# JIT 與逃逸分析

## 面試問題

JVM 的 JIT 編譯大概做什麼？逃逸分析（escape analysis）能帶來哪些優化？

## 答法

- **解釋執行 vs JIT**：熱點方法被反覆執行後，JIT 把它編成機器碼，後續直接跑原生碼，比純解釋快很多。
- **熱點偵測**：方法計數 / 回邊計數；達到閾值觸發編譯（C1 偏快、C2 偏猛，視 JVM 版本與分層編譯）。
- **逃逸分析**：分析對象會不會「逃出」方法或執行緒。
  - **不逃逸**：可做 **棧上分配**（或不真分配到堆）、**標量替換**（把對象拆成局部變數）、鎖消除。
  - **執行緒逃逸但不方法逃逸**：仍可能做部分優化。
- **面試一句話**：JIT 把熱點變快；逃逸分析讓「看起來 new 了」的對象有時根本沒進堆、鎖也可能被消掉。

## 常見追問 / 陷阱

「看到 `new` 就一定有堆分配？關掉逃逸分析效能一定變差？」

→ 不逃逸時可能沒有真實堆分配；優化依賴分析結果與編譯閾值，別把「源碼有 new」等同「一定 GC 壓力」。生產上少手動關 EA，除非在做對照實驗。

## 小練習

一個方法裡 `new` 一個只在本方法用的臨時對象、從不 return / 存到欄位，JIT 開著時，面試時你怎麼描述它的分配行為？

---

## 深入（2026-11-10）：標量替換、鎖消除、點樣「證明」同常見誤區

### 面試問題

面試官問：方法裡 `new` 咗個臨時對象、又對一個只喺方法內可見嘅鎖做 `synchronized`，JIT 開著時分配同加鎖會發生咩？你點同「源碼有 new／synchronized」區分？生產上點觀察？

### 答法

**逃逸程度（講得出層級就加分）**

| 程度 | 意思 | 常見後果 |
|------|------|----------|
| NoEscape | 唔出方法（唔 return、唔存欄位、唔傳畀可能存落去嘅呼叫） | 可做**標量替換**（拆成局部變數，唔真喺堆分配）、**鎖消除** |
| ArgEscape | 傳入呼叫但被調方唔再讓佢逃 | 優化空間收窄，視內聯同分析結果 |
| GlobalEscape | return／存欄位／丟去別線程可見結構 | 必須堆分配；鎖唔能消 |

**同後端面試相關嘅三點**

1. **標量替換 ≠「一定棧上分配」**：HotSpot 更常見係把對象拆散成寄存器／局部變數，看起來「冇咗呢個對象」。所以「一定有 TLAB／堆分配」係錯嘅口頭禪。
2. **鎖消除**：`synchronized` 包住一個從不逃逸嘅對象（或 JIT 證明冇共享），鎖可以消掉。反例：鎖對象係 `this`／靜態／成員，或者對象被別線程見到 → 消唔到。
3. **同 GC／P99 嘅關係**：熱路徑上大量「其實 NoEscape」嘅臨時對象，理想情況幾乎唔進堆；一旦你改成 return DTO、塞進 List 回傳、或者丟去 `@Async`／線程池 → 變 GlobalEscape，分配同 GC 壓力會「無端」升。

**點觀察（唔好背旗標名充數）**

- 對照實驗：同一基準，開／關逃逸相關優化（了解即可；生產少手動關），睇分配速率同 P99。
- JFR / async-profiler：睇 **allocation** 同編譯事件；發佈後毛刺要聯想[預熱與去優化](jit-warmup-deoptimization.md)。
- 源碼有 `new` 只係**候選**；最終行為睇 JIT 有冇編譯、有冇內聯、逃逸分析結果。

### 追問／陷阱

- 「關掉逃逸分析一定變慢？」→ 多數熱路徑會差，但唔係每個 microbenchmark 都敏感；唔好當線上調優旋鈕亂關。
- 「`synchronized (new Object()) { ... }` 仲有冇鎖？」→ 理論上可被消除；面試重點係**證明有冇逃逸**，唔係背結論。
- 對象傳入日誌框架、Metrics、`CompletableFuture`、線程池任務 → 好易變逃逸，優化假設被打破。
