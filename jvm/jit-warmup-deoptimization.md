# JIT 預熱與去優化：發佈後 P99 毛刺

> 延伸自 [JIT 與逃逸分析](jit-escape-analysis.md)，這篇講線上實戰角度。

## 面試問題

新版本發佈後頭幾分鐘 P99 很高，過一陣自己好了。為什麼？怎麼處理？

## 答法

- **分層編譯**：代碼先解釋執行 → 熱了交給 C1（快編、輕優化）→ 更熱交給 C2（慢編、激進優化）。剛啟動時大部分熱點代碼還在解釋執行，慢幾倍到幾十倍。
- **冷啟動不只 JIT**：類加載、連接池未建滿、本地緩存是空的、JIT 編譯線程本身在搶 CPU（容器 CPU limit 小時特別明顯）。
- **處理**：
  - readiness 通過前先**預熱**：打一批接近真實的請求（或回放流量）。
  - 負載均衡**慢啟動**：新實例權重逐步放大，不要一上來吃滿流量。
  - 連接池 `minIdle` 預建、熱數據提前載入本地緩存。
  - 啟動階段給夠 CPU；類加載多可考慮 AppCDS（JDK 新版本還有 AOT cache）。

## 常見追問／陷阱

- **去優化（deoptimization）**：C2 按運行時 profile 做假設，例如「這個接口只見過一個實現 → 直接內聯」「這個分支從沒走過 → 不編」。假設被打破（新實現被加載、冷分支突然被走）就退回解釋執行再重編，表現是**跑得好好的突然慢一下**。`-XX:+PrintCompilation` 裡看到 `made not entrant` 就是。
  - 所以預熱流量要**像真實流量**；只打健康檢查或單一接口，profile 偏了，真實流量一來反而觸發去優化。
- **Code Cache 滿**：日誌出現 `CodeCache is full. Compiler has been disabled.` → 之後新熱點不再編譯，性能斷崖。看 `ReservedCodeCacheSize`，大應用要調大並監控。
- 一句話：**發佈毛刺 = 代碼還沒「熱」+ 資源還沒「暖」**；解法是預熱 + 慢放量，而不是一味加機器。
