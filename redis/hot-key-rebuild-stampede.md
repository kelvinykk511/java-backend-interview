# 熱點 Key 重建（擊穿／Stampede）

## 面試問題

熱點緩存剛好過期，瞬間幾千請求同時 miss，怎麼避免一起打垮 DB？（和穿透、雪崩怎麼分）

## 答法

**先對齊名詞（別混）**

- **擊穿（stampede）**：一個**熱點** key 過期 → 併發重建打 DB。
- **穿透**：key **根本不存在** → 每次都打 DB（空結果也要短 TTL／布隆）。
- **雪崩**：大量 key **同時**過期，或 Redis 掛了 → 流量整體砸庫。

**三種重建策略（面試主線）**

1. **互斥鎖 / Singleflight**：只有拿到鎖的請求查 DB 並回寫；其他人短暫等待或讀舊值。代價：鎖超時、單點重建延遲。
2. **邏輯過期**：value 裡帶 `expireAt`，物理上永不過期；過期後仍返回舊值，並**異步**觸發一次重建。代價：短暫讀到舊數據（可接受則很香）。
3. **熱點永不（或極長）過期 + 主動更新**：寫路徑刪/更新緩存；讀路徑幾乎不 miss。代價：寫複雜、要防漏更新。

面試口訣：**熱點少用「純 TTL 到期再全員重建」；用鎖串行化，或邏輯過期換一致性窗口。** 可接受舊值 → 優先邏輯過期；要強一致 → 互斥＋超時降級。

**實作細節（加分）**

- 鎖用 Redis `SET key token NX PX`，釋放要核對 token（防誤刪別人的鎖）。
- **等待方必須設超時**：否則 miss 潮下「等鎖」把 Tomcat／業務線程池與隊列打滿——DB 還沒倒，HTTP 先 503／超時雪崩（Spring MVC 尤其痛）。
- 空結果仍要短 TTL 緩存，否則擊穿修了、穿透還在。

## 常見追問 / 陷阱

「加分布式鎖重建，是不是就 Exactly-Once 寫入緩存了？」

→ 鎖只保證「同時只有一個去查 DB」。DB 查完、寫 Redis 前進程掛了，別人還會再查一次——**可接受的重複查庫**，不是業務冪等問題。別把緩存重建鎖和「扣款冪等」混談。另：**鎖＋無限等待 = 線程池排隊陷阱**，跟「有沒有鎖」一樣常考。

## 小練習

秒殺商品詳情頁，QPS 極高、可接受 1～2 秒舊庫存展示：互斥鎖和邏輯過期你選哪個？為什麼？若選互斥，等待超時與線程池隊列要怎麼設才不會先把自己打掛？

## 深入（2026-11-13）：熱 key ≠ 擊穿，CEX 行情價點防

### 面試可以點追

「BTCUSDT 最新成交價緩存在一個 Redis key，平常 Redis CPU 已經偏高；key 一過期 MySQL 被打爆。熱 key、擊穿、穿透有咩分別？加把分布式鎖就夠未？」

### 答法

**三個詞分清（同 11-09 穿透筆記對照）**

| 問題 | 特徵 | 典型防法 |
|------|------|----------|
| **穿透** | key **從不存在** → 每次打 DB | Bloom／空值短 TTL（見 [布隆與穿透](bloom-filter-penetration.md)） |
| **擊穿（stampede）** | **一個熱點** key 剛好過期 → 併發重建打 DB | 互斥／singleflight、邏輯過期、寫路徑主動更新 |
| **熱 key** | 就算**未過期**，流量集中喺極少 key → Redis 單線程／單分片被打滿 | 本地緩存、過期抖動、讀 replica、拆 key／多副本快照 |

CEX 典型熱 key：標記價／指數價、盤口最優價、熱門幣對 ticker、熱門用戶持倉。擊穿修嘅係「別一起打 DB」；熱 key 修嘅係「別所有讀都打同一個 Redis key」。兩者成對出現，只鎖 DB 重建解決唔到 Redis CPU。

**重建：鎖只串行化查庫**

- 互斥鎖／singleflight：一人查 DB 回寫，其他人短等或讀舊值。鎖用 `SET key token NX PX`，釋放核對 token。
- **等鎖一定要超時／立即降級**：無限忙等會令 Tomcat／網關線程池先滿，DB 還沒倒，接口已經 503。
- 邏輯過期：物理不過期，value 帶 `expireAt`；過期仍回舊值，**異步**觸發一次重建。可接受 1～2 秒舊行情時，呢個通常比互斥更穩。
- 熱點極長 TTL + 寫路徑主動更新：讀路徑幾乎不 miss。

**熱 key 本體：先擋在應用進程**

- 進程內 Caffeine／單飛（`compute`／Guava `LoadingCache`）：同一個 JVM 只打 Redis／DB 一次。
- 本地同 Redis TTL **加隨機抖動**，避免多 Pod 同時啟動或同時過期變成「對齊 stampede」。
- Redis Cluster 下一個熱 key 只落喺**一個 slot／一個節點**；監控 `hotkeys`、單分片 CPU、該 key QPS。讀多可考慮副本讀或把快照拆到多個只讀 key（視一致性窗口）。

### 追問／陷阱

「有分布式鎖就係只查一次 DB？」→ 否。鎖 TTL 短過重建時間會再放一群人進去；重建中間進程掛了，別人會再查一次——緩存重建允許重複查庫，唔好同扣款冪等混談。另一陷阱：所有 Pod 只做 Redis 層 singleflight、進程內無互斥，20 個實例仍可能 20 次同時查庫，而且等鎖期間 Redis 本身仲係熱 key。
