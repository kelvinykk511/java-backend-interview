# Redis 緩存與 DB 雙寫一致性

> 延伸自 [Cache-Aside 與穿透/擊穿/雪崩](cache-aside-penetration-breakdown-avalanche.md)

## 面試問題
用 Redis 做緩存，更新數據時點樣保證緩存同 DB 一致？「先刪緩存再更新 DB」同「先更新 DB 再刪緩存」邊個好？

## 答法
- **前提**：緩存同 DB 冇分布式事務，只能做到**最終一致**；要強一致就唔好緩存，或者讀走 DB。
- **刪，唔好更新緩存**：並發兩個寫可能令緩存停喺舊值（A 寫 DB→B 寫 DB→B 寫緩存→A 寫緩存）；而且緩存值可能要計算，寫多讀少時白做。
- **先刪緩存再更新 DB（唔推薦）**：刪完到寫 DB 之間，讀請求 miss→讀舊 DB→回填舊值，之後一直髒到 TTL。窗口 = 寫 DB 時間，好大。
- **先更新 DB 再刪緩存（主流 Cache-Aside）**：仍有極小窗口：讀 miss 讀到舊值 → 寫 DB + 刪緩存 → 讀者先至回填舊值。要「讀 DB 慢過寫 DB+刪」先中，機率低。
- **刪除失敗點算**：重試（MQ 重試隊列），或者 **訂閱 binlog（Canal/Debezium）異步刪緩存**——業務代碼唔使理，DB commit 咗先觸發，最可靠。
- **延遲雙刪**：更新 DB → 刪 → sleep N（> 一次讀 DB+回填時間，通常幾百 ms）→ 再刪。用嚟收窄上面嘅窗口；N 靠估，唔係保證。
- **兜底**：所有 key 都要有 TTL（加隨機抖動），最差情況髒到 TTL 為止。

## 常見追問 / 陷阱
- **讀寫分離 + 緩存**：刪完緩存，讀 miss 去**從庫**讀到舊值回填 → 髒。解法：回填走主庫，或者用 binlog 刪 + 延遲雙刪（延遲 > 主從延遲）。
- **強一致要求（例如餘額）**：唔好靠緩存；或者用分布式鎖/版本號（寫入帶 version，回填時 `version` 舊過就唔寫）。
- 「點解唔用事務包住 DB+Redis？」→ Redis 唔參與 DB 事務，rollback 唔會還原 Redis。

## 一句總結
先更新 DB，再刪緩存；刪失敗靠重試/binlog；從庫延遲靠回填走主或延遲雙刪；TTL 兜底。
