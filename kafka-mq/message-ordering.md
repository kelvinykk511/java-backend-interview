# Kafka 消息順序：怎樣保證同一訂單的事件不亂序

> 面試題：訂單有「創建 → 支付 → 發貨」三個事件，下游偶爾先收到「支付」再收到「創建」。Kafka 怎樣保證順序？

## 核心結論

- Kafka 只保證**單個分區內**有序，跨分區無序。
- 要「同一訂單有序」：用 `orderId` 當 **message key**，同 key 哈希到同一分區。
- 不需要全局有序；全局有序 = 單分區，吞吐上不去。

## 生產端：重試可能亂序

- `retries > 0` 且 `max.in.flight.requests.per.connection > 1`：批次 1 失敗重試、批次 2 先成功 → 分區內亂序。
- 解法：開 **冪等 producer**（`enable.idempotence=true`，3.0+ 默認開），broker 用 PID + 序號拒絕亂序/重複，`max.in.flight ≤ 5` 下仍保序。
- 舊版本沒冪等：只能 `max.in.flight=1`（吞吐差）。
- 異步 send 回調裡「失敗後自己再 send 一次」→ 這條會排到後面，**應用層重試會打亂順序**。

## 消費端：最常見的亂序來源

- 一個分區只會分給組內一個 consumer，本身有序。
- 但拉到一批後丟進**線程池並發處理** → 亂序。解法：按 key 哈希到固定線程/內存隊列（同 key 同線程），或每分區單線程處理。
- 處理失敗丟去重試 topic 再回來 → 也會亂序；需要阻塞重試，或後續同 key 消息也要排隊。

## 擴分區的坑

- 增加分區後 `hash(key) % N` 變了 → 同一訂單的新消息可能去了新分區，切換瞬間新舊分區並行消費 → 短暫亂序。
- 有序 topic 預先規劃分區數；必須擴時先停寫/排空或接受短暫窗口。

## 兜底：業務上容忍亂序

- 消息帶**版本號/狀態機**：下游只接受「比當前更新」的狀態（如 `UPDATE ... WHERE version < ?`），舊消息直接丟。
- 收到「支付」但訂單不存在：暫存/延遲重試，而不是報錯丟棄。
- 面試加分：「Kafka 保證分區有序是基礎，真正可靠是下游用版本號做冪等 + 狀態機。」

## 常見追問

- **rebalance 會亂序嗎？** 分區換 consumer 時，舊 consumer 沒提交 offset → 新 consumer 重新消費部分消息 → 重複（不是亂序）；靠冪等解決。
- **熱點 key 怎麼辦？** 一個大客戶的 key 全打一個分區 → 傾斜；可以只對需要有序的維度做 key（如 `orderId` 而非 `userId`）。
