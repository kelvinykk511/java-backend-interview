# Kafka 消息順序：怎樣保證同一訂單／同一筆充值唔亂序

## 面試問題

訂單有「創建 → 支付 → 發貨」，或者充值有「上鏈確認 → 入帳 → 通知」。下游偶爾先收到後面嗰步。Kafka 點保證同一筆業務有序？開咗冪等 producer 係咪就夠？消費端最常見嘅亂序來源係乜？

## 答法

**核心邊界**

- Kafka **只保證單個分區內有序**，跨分區無序。
- 要「同一訂單／同一筆充值有序」：用 `orderId`／`depositId` 當 **message key**，同 key 哈希到同一分區。
- 唔需要全局有序；全局有序 = 單分區，吞吐上唔去。用戶維度（`uid`）可以保「同一用戶有序」，但大戶會變成熱點分區，通常只對**需要有序嘅業務單號**做 key。

**生產端：重試可能亂序**

- `retries > 0` 且 `max.in.flight.requests.per.connection > 1`：批次 1 失敗重試、批次 2 先成功 → 分區內亂序。
- 解法：開 **冪等 producer**（`enable.idempotence=true`，3.0+ 預設開），broker 用 PID + 序號拒絕亂序／重複，`max.in.flight ≤ 5` 下仍保序。
- 舊版本冇冪等：只能 `max.in.flight=1`（吞吐差）。
- **冪等救唔到應用層再 send**：異步 callback 裡「失敗後自己再 `send` 一次」，係一條**新紀錄**（新序號），會排到後面，分區內就亂咗，仲可能重複。應靠 producer 自己重試，或者業務冪等鍵，唔好在 callback 另發一條當重試。

**消費端：最常見嘅亂序來源**

- 一個分區同一時間只會分畀組內一個 consumer，拉下來本身有序。
- 但拉到一批後丟進**線程池並發處理** → 亂序。解法：按 key 哈希到固定線程／內存隊列（同 key 同線程），或每分區單線程處理。
- 處理失敗扔去 **retry topic** 再回來 → 後續消息可能已經先做完。要嘛阻塞重試（暫停呢個 key／分區），要嘛後續同 key 一齊排隊，再加狀態機兜底。
- 先處理後提交 offset 仍然只解決「至少一次／重複」，**唔解決並發帶來嘅亂序**。

**擴分區嘅坑**

- 增加分區後 `hash(key) % N` 變咗 → 同一業務單嘅新消息可能去咗新分區，切換瞬間新舊分區並行消費 → 短暫亂序。
- 有序 topic 預先規劃分區數；必須擴時先停寫／排空，或接受短暫窗口並靠下游版本號。

**兜底：業務上容忍亂序**

- 消息帶**版本號／狀態機**：下游只接受「比當前更新」嘅狀態（如 `UPDATE ... WHERE version < ?`），舊消息直接丟。
- 收到「支付／入帳」但上游單仲未見：暫存或延遲重試，唔好當錯誤丟棄之後再也接唔返。
- 面試加分：Kafka 保證分區有序只係基礎，真正可靠係下游用版本號做冪等 + 狀態機。

## 常見追問 / 陷阱

- **開咗冪等 producer 就一定有序？** 只保「同一 producer、同一分區、由客戶端重試」嘅不重不亂。Callback 再 send、消費並發、retry topic、擴分區，一樣會亂。
- **rebalance 會亂序嗎？** 分區換 consumer 時，舊 consumer 未提交 offset → 新 consumer 重放部分消息 → 多數係**重複**而唔係亂序；靠下游冪等。若舊 consumer 已經處理中、新 consumer 同時再跑，先要停妥再交分區（cooperative sticky 減少震動，但唔能當保序方案）。
- **熱點 key？** 一個大客戶用 `uid` 當 key，整條分區被打滿。需要有序就用更細嘅 `orderId`／`depositId`；要按用戶串行先考慮本地隊列，而唔係把所有用戶事件塞進同一分區。
- **事務 producer／EOS 同順序：** 事務提交後分區內仍然有序，但跨分區只保證「都可見或都唔見」，唔保證跨分區到達順序。`isolation.level=read_committed` 避免消費到未提交事務。
