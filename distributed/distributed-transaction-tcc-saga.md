# 分布式事務：2PC / TCC / Saga / 本地消息表

**Q:** 下單要「扣庫存（庫存服務）+ 扣餘額（賬戶服務）+ 建訂單（訂單服務）」，三個服務各自有 DB。你點保證唔會扣咗錢冇訂單？

## 幾種方案對比
| 方案 | 一致性 | 做法 | 適合 |
|---|---|---|---|
| 2PC / XA（Seata AT 類似思路） | 強一致 | 協調者先 prepare 全部，全部 OK 先 commit | 低併發、內部系統；鎖資源時間長 |
| TCC | 最終一致（業務層強控制） | Try 預留資源（凍結）→ Confirm 真扣 / Cancel 釋放 | 資金、庫存等要精準控制 |
| Saga | 最終一致 | 每步本地事務直接提交，失敗就逆序執行補償 | 長流程、跨外部系統 |
| 本地消息表 / Outbox + MQ | 最終一致 | 業務同「待發消息」同一本地事務寫入，再可靠投遞 | 最常用，下游異步可接受 |

## TCC 三大坑（面試必問）
- **冪等**：Confirm/Cancel 可能被重試多次 → 用事務 ID 記錄狀態，重複調用直接返回。
- **空回滾**：Try 因網絡超時根本冇執行，協調者就叫 Cancel → Cancel 要識別「冇 Try 記錄」直接成功，唔好亂加餘額。
- **懸掛**：Cancel 已經執行完，遲到的 Try 先到 → Try 前檢查已有 Cancel 記錄就拒絕，否則資源永遠凍結。

## Saga 要點
- 補償唔係 rollback，係反向業務操作（退款、加返庫存），本身都要冪等、要可重試。
- 冇隔離性：中間狀態對外可見（例如錢已扣、訂單未建），要用狀態機（PENDING）擋住。

## 追問 / 陷阱
- 「點解唔全部用 2PC？」→ 協調者單點、prepare 期間一直鎖行，高併發吞吐差；MySQL XA 喺故障恢復時有懸而未決事務要人工處理。
- 「交易所提幣/充值點揀？」→ 資金類用 TCC 思路（凍結→確認/解凍）+ 對賬兜底；通知類用 Outbox，見 [transactional-outbox](transactional-outbox.md)、[idempotency](idempotency.md)。
- 無論揀邊個，**定時對賬**係最後防線。

## 深入：出金凍結用 TCC，通知先用 Outbox（2026-11-25 warm-up）

**面試題**：出金要「凍結餘額 + 調簽名機／打鏈 + 記出金單」，幾個服務各自有 DB。2PC、TCC、Saga、Outbox 你點揀？Try 超時之後 Cancel、遲到的 Try、Confirm 重試，會出咩問題？

- **點揀**。2PC／XA 係強一致，但 prepare 期間鎖行、協調者故障同恢復都貴，高併發資金鏈唔合適。TCC 用業務層預留：Try 凍結 → Confirm 真扣／Cancel 解凍，適合餘額、庫存呢類「要先佔住再對外呼叫」嘅資源。Saga 每步本地事務直接提交，失敗就做**反向業務**（唔係 rollback），中間狀態對外可見，要用狀態機擋住。Outbox 係「本地事務同待發消息一起提交，再可靠投遞」，適合通知、記流水、驅動下游，**替代唔到凍結**。
- **交易所常見切法**：出金／劃轉先走 TCC 思路（凍結 → 成功打鏈先 Confirm，失敗或超時 Cancel 解凍）；通知撮合、審計事件走 [Outbox](transactional-outbox.md)。定時對賬係最後防線，唔可以只信協調器。
- **點解 Outbox 替代唔到 TCC**：Outbox 保證嘅係「本地已提交嘅事實一定會發出去」，但錢喺發出去之前已經要被佔住。若只寫「扣款消息」再異步扣，對方可先花、你先超時重發，對唔齊。對外打鏈／調簽名機之前，必須先凍結。
- **點解鏈上出金唔能只靠 Saga 補償**：補償係反向業務（加返餘額）。交易若已經廣播、甚至已經上鏈，你加返餘額會變成超發。呢類步驟一旦過咗不可逆邊界，就只能 Confirm（記 txid）＋對賬／人工，唔能當普通「失敗就補償」。

### TCC 三個時序坑（要用事務 ID 做狀態機）

- **冪等**：網絡超時之下 Confirm／Cancel 一定會被重試。記錄 `txId → TRY_SUCCESS / CONFIRMED / CANCELED`，重複請求直接返回當前成功態，切忌再扣一次或再加一次。
- **空回滾**：Try 因超時／丟包**根本冇執行**（或請求還在路上），協調者已經發 Cancel。Cancel 見到冇 Try 記錄都要**當成功**，並留下「已取消」標記，唔好當「冇單就加返餘額」。
- **懸掛**：Cancel 已經成功，遲到的 Try 先到。Try **必須先查已取消就拒絕**，否則會凍結一筆永遠冇人 Confirm／再 Cancel 都對唔齊嘅資金。

### 追問

- 「全部用 2PC 最穩？」鎖時間長、MySQL XA 故障後可能留懸而未決事務，吞吐同運維都唔划算。
- 「Confirm 超時係咪當失敗，再 Try 一次？」唔係。超時結果未知，要按 `txId` 查狀態或重試**同一個 Confirm**，唔好開一筆新嘅凍結。
- Saga 中間態（錢已扣、單未建）要 `PENDING`／凍結單擋住用戶再花；補償動作本身都要冪等、可重試。
