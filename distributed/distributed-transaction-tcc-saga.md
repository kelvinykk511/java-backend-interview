# 分布式事務：2PC / TCC / Saga / 本地消息表

**Q:** 下單要「扣庫存（庫存服務）+ 扣餘額（賬戶服務）+ 建訂單（訂單服務）」，三個服務各自有 DB。你點保證唔會扣咗錢冇訂單？

## 幾種方案對比
| 方案 | 一致性 | 做法 | 適合 |
|---|---|---|---|
| 2PC / XA（Seata AT 類似思路） | 強一致 | 協調者先 prepare 全部，全部 OK 先 commit | 低併發、內部系統；鎖資源時間長 |
| TCC | 最終一致（業務層強控制） | Try 預留資源（凍結）→ Confirm 真扣 / Cancel 釋放 | 資金、庫存等要精準控制 |
| Saga | 最終一致 | 每步本地事務直接提交，失敗就逆序執行補償 | 長流程、跨外部系統 |
| 本地消息表 / Outbox + MQ | 最終一致 | 業務同「待發消息」同一本地事務寫入，再可靠投遞 | 最常用，下游異步可接受 |

## TCC 三大坑（面試必問）
- **冪等**：Confirm/Cancel 可能被重試多次 → 用事務 ID 記錄狀態，重複調用直接返回。
- **空回滾**：Try 因網絡超時根本冇執行，協調者就叫 Cancel → Cancel 要識別「冇 Try 記錄」直接成功，唔好亂加餘額。
- **懸掛**：Cancel 已經執行完，遲到的 Try 先到 → Try 前檢查已有 Cancel 記錄就拒絕，否則資源永遠凍結。

## Saga 要點
- 補償唔係 rollback，係反向業務操作（退款、加返庫存），本身都要冪等、要可重試。
- 冇隔離性：中間狀態對外可見（例如錢已扣、訂單未建），要用狀態機（PENDING）擋住。

## 追問 / 陷阱
- 「點解唔全部用 2PC？」→ 協調者單點、prepare 期間一直鎖行，高併發吞吐差；MySQL XA 喺故障恢復時有懸而未決事務要人工處理。
- 「交易所提幣/充值點揀？」→ 資金類用 TCC 思路（凍結→確認/解凍）+ 對賬兜底；通知類用 Outbox，見 [transactional-outbox](transactional-outbox.md)、[idempotency](idempotency.md)。
- 無論揀邊個，**定時對賬**係最後防線。
