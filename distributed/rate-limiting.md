# 限流算法：固定窗口、滑動窗口、令牌桶、漏桶

## 面試問題

交易所下單 API 要限制「每個用戶每秒最多 10 單」，集群有 20 台網關。你會選哪種限流算法？單機和分佈式分別怎麼做？

## 答法

**四種算法一句話**

| 算法 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| 固定窗口 | 每秒一個計數器，超過拒絕 | 最簡單 | **窗口邊界突刺**：0.9s 打 10、1.1s 再打 10，0.2s 內 20 單 |
| 滑動窗口 | 統計「過去 1 秒」的請求（日誌式用 ZSet 存時間戳，或分多個小格子） | 平滑、精確 | 日誌式內存大；格子式是近似 |
| 令牌桶 | 以固定速率往桶裡放令牌，請求拿到令牌才過；桶有容量 | **允許短時突發**（桶滿時），長期平均受控 | 要選好容量和速率 |
| 漏桶 | 請求進隊列，以固定速率流出 | 輸出**絕對平滑** | 不允許突發，排隊增加延遲 |

**選型**：API 限流通常用**令牌桶**（用戶偶爾連點可以容忍，長期速率受控）；保護下游（例如撮合引擎、第三方接口）要絕對平滑時用**漏桶**。

**單機 vs 分佈式**

- 單機：Guava `RateLimiter`（令牌桶）、Resilience4j / Sentinel。問題：20 台各限 10 = 實際 200，且負載不均時不準。
- 分佈式：Redis + **Lua 腳本**保證「讀-算-寫」原子（令牌桶存 `tokens` + `last_refill_ts`，或固定窗口 `INCR` + `EXPIRE`）。key 按 `userId` 設計；Redis Cluster 下單 key 操作沒有跨 slot 問題。
- 折衷：全局配額按機器數下發給本地限流（不精確但不依賴 Redis 每次調用），或熱點用戶單獨走 Redis。

**落地要點**：被限流回 **HTTP 429** + `Retry-After`；分維度（IP、用戶、API Key、接口）；**Redis 掛了的策略要事先定**——fail-open（放行，保可用）還是 fail-closed（拒絕，保下游），下單接口通常要結合下游保護決定。

## 常見追問 / 陷阱

「`INCR` 後再 `EXPIRE` 兩條命令有什麼問題？」→ 不是原子，進程在中間掛了 key 永不過期 → 用戶被永久限流。用 Lua 或 `SET key 0 EX 1 NX` + `INCR`。陷阱二：限流 ≠ 熔斷——限流管「進來多少」，熔斷管「下游壞了就別再打」，兩者常一起出現。

## 小練習

活動開盤瞬間，某做市商 API Key 在 50ms 內發了 30 單，限額每秒 10 單。分別說出固定窗口、令牌桶（容量 10、速率 10/s）、漏桶下，這 30 單大概會怎樣被處理。
