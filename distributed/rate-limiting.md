# 限流算法：固定窗口、滑動窗口、令牌桶、漏桶

## 面試問題

交易所下單 API 要限制「每個用戶每秒最多 10 單」，集群有 20 台網關。你會選哪種限流算法？單機和分佈式分別怎麼做？

## 答法

**四種算法一句話**

| 算法 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| 固定窗口 | 每秒一個計數器，超過拒絕 | 最簡單 | **窗口邊界突刺**：0.9s 打 10、1.1s 再打 10，0.2s 內 20 單 |
| 滑動窗口 | 統計「過去 1 秒」的請求（日誌式用 ZSet 存時間戳，或分多個小格子） | 平滑、精確 | 日誌式內存大；格子式是近似 |
| 令牌桶 | 以固定速率往桶裡放令牌，請求拿到令牌才過；桶有容量 | **允許短時突發**（桶滿時），長期平均受控 | 要選好容量和速率 |
| 漏桶 | 請求進隊列，以固定速率流出 | 輸出**絕對平滑** | 不允許突發，排隊增加延遲 |

**選型**：API 限流通常用**令牌桶**（用戶偶爾連點可以容忍，長期速率受控）；保護下游（例如撮合引擎、第三方接口）要絕對平滑時用**漏桶**。

**單機 vs 分佈式**

- 單機：Guava `RateLimiter`（令牌桶）、Resilience4j / Sentinel。問題：20 台各限 10 = 實際 200，且負載不均時不準。
- 分佈式：Redis + **Lua 腳本**保證「讀-算-寫」原子（令牌桶存 `tokens` + `last_refill_ts`，或固定窗口 `INCR` + `EXPIRE`）。key 按 `userId` 設計；Redis Cluster 下單 key 操作沒有跨 slot 問題。
- 折衷：全局配額按機器數下發給本地限流（不精確但不依賴 Redis 每次調用），或熱點用戶單獨走 Redis。

**落地要點**：被限流回 **HTTP 429** + `Retry-After`；分維度（IP、用戶、API Key、接口）；**Redis 掛了的策略要事先定**——fail-open（放行，保可用）還是 fail-closed（拒絕，保下游），下單接口通常要結合下游保護決定。

## 常見追問 / 陷阱

「`INCR` 後再 `EXPIRE` 兩條命令有什麼問題？」→ 不是原子，進程在中間掛了 key 永不過期 → 用戶被永久限流。用 Lua 或 `SET key 0 EX 1 NX` + `INCR`。陷阱二：限流 ≠ 熔斷——限流管「進來多少」，熔斷管「下游壞了就別再打」，兩者常一起出現。

## 小練習

活動開盤瞬間，某做市商 API Key 在 50ms 內發了 30 單，限額每秒 10 單。分別說出固定窗口、令牌桶（容量 10、速率 10/s）、漏桶下，這 30 單大概會怎樣被處理。

## 深入（2026-11-15）：集群配額、Lua 原子性、熱 key 同降級

### 面試可以點追

20 個網關 Pod，每個 API Key 每秒最多 10 單。單機 `RateLimiter` 夠唔夠？Redis 固定窗口 `INCR` 有咩坑？限流 Redis 超時，或者被做市商打成熱 key，你會點設計？

### 答法

**單機先唔夠**

- 每 Pod 限 10/s，20 個 Pod 就係 200/s；負載不均時仲會更歪。要按 `apiKey`（或 userId）做**全局**配額。
- 算法仍然：對客 API 多用**令牌桶**（允許短突發、長期均值受控）；保護撮合／下游要用更平滑嘅漏桶，或者更細嘅配額。固定窗口有**邊界突刺**（窗口末 + 窗口初可以接近 2 倍額度）。

**分布式落地**

- Redis + **Lua** 原子讀-算-寫。令牌桶存 `tokens` + `last_refill_ts`；時間用 Redis `TIME`，避免多機時鐘偏斜。
- 固定窗口起碼把 `INCR` 同過期放喺同一原子腳本。`INCR` 再 `EXPIRE` 兩次往返，中間進程掛會令 key 永不過期，用戶被永久限流。
- 被拒回 **429** + `Retry-After`。維度拆開：未授權先限 IP，授權後限 API Key／用戶／接口，必要時再加幣對。
- Redis Cluster：單 key 操作唔跨 slot；但熱門做市商一個 key 會打同一 slot，**限流本身可以變成熱 key**。

**熱點同降級**

- 熱 key：本地先加一層細配額／單機令牌桶擋尖峰，再問 Redis；或者把熱 key 拆成多個分片計數再彙總（犧牲一點精度）。要監控該 slot CPU。
- Redis 超時／故障要預先定策略。下單接口對下游嘅保護，通常 **fail-closed**，或者「本地保守限流後先放少量」。純 **fail-open** 喺開盤時 Redis 一抖，等於取消限流，撮合會被打爆。
- 限流路徑本身要設短超時同隔離，唔可以變成每個請求都卡死喺 Redis。

### 追問／陷阱

- 限流 ≠ 熔斷：限流管進來多少，熔斷管下游壞咗就停打。
- 「按機器數把 10/s 拆成每機 10/20」只係近似，彈性伸縮要重算；熱點用戶仍然要走全局 Redis。
- 令牌桶容量=10、速率=10/s，50ms 內來 30 單：最多先過 **10**（桶容量），其餘拒絕，之後按速率補令牌——唔係 30 張都過，亦唔等於固定窗口喺邊界可以放 20。
