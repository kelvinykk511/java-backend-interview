# 介面與消息的冪等

## 面試問題

什麼叫冪等？後端寫操作（下單、扣款、消費 MQ）怎麼保證重複請求不會搞壞數據？

## 答法

**定義（一句話）**

同一操作執行一次和執行多次，對系統狀態的影響一樣。

**為什麼需要**

- 客戶端重試、網關超時重放、Kafka「至少一次」都會讓同一業務請求進來多次。
- 交易所場景：充提、下單、撮合回調，重複執行一次就可能錯帳。

**常見做法（由淺到深）**

1. **業務唯一鍵**：客戶端帶 `requestId` / `orderId`，DB 唯一約束；撞到就當已成功返回。
2. **狀態機**：只允許 `PENDING → SUCCESS`，重複請求看到終態直接返回，不重做副作用。
3. **Token / 去重表**：Redis `SETNX key ttl` 或去重表記「這筆已處理」。
4. **天然冪等**：`UPDATE ... SET balance = ?` 用絕對值，比「加減一次」更安全（仍要防併發用版本號/樂觀鎖）。

面試口訣：**識別鍵 + 唯一約束/去重 + 狀態機**，比空談「加鎖」更像實戰。

## 常見追問 / 陷阱

「加了分布式鎖就冪等了嗎？」

→ 鎖只防併發，不防「第一次已成功、鎖釋放後重試又進來」。還是要有「這筆業務 ID 已完成」的記錄。
