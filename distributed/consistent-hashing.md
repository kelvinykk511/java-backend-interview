# 一致性雜湊（Consistent Hashing）

## 面試問題

緩存節點加減時，為什麼常用一致性雜湊而不是 `hash % N`？虛擬節點在解決什麼？

## 答法

- **`hash % N`**：N 一變，幾乎所有 key 映射全變 → 緩存雪崩式失效 / 數據大遷移。
- **一致性雜湊**：把節點與 key 都映射到同一個環上；key 順時針找第一個節點。加減一台，通常只影響鄰近一小段 key。
- **虛擬節點（vnode）**：一台物理機在環上掛很多虛擬點，負載更均勻，也避免「節點太少時傾斜」。
- **面試一句話**：一致性雜湊降低「變節點數」時的震動；vnode 解決均勻與熱點。Redis Cluster 用的是槽位（16384），思路相近但實現不同——別混成同一套。

## 常見追問 / 陷阱

「一致性雜湊能保證每台負載一樣嗎？」

→ 不能保證絕對均勻；節點少或 key 分佈偏斜時仍會熱點。所以要 vnode，且熱 key 還要業務層拆分（本地緩存、打散 key）。

## 小練習

CEX 把某用戶 session / 限流計數放在自建緩存集群。加機器時你選 `hash % N` 還是一致性雜湊？要不要 vnode？一句話理由。

## 深入（2026-10-31 補充）

### 面試問題

自己實現一致性雜湊路由，點做？加節點時有咩實際問題？同 Redis Cluster 槽位比有咩分別？

### 答法

- **實現**：`TreeMap<Long, Node>` 做環；key 算 hash 後 `ceilingEntry(hash)`，搵唔到就繞返 `firstEntry()`。
- **hash 函數**：用 MurmurHash / xxHash / MD5，唔好用 `String.hashCode()`（分佈差，相似 key 會擠埋一齊）。
- **虛擬節點數**：每台常見 100–200 個；想按機器配置分權重，就畀強啲嘅機器多啲 vnode。
- **加一台**：理論上只搬約 `1/(N+1)` 嘅 key，但嗰批 key 喺新節點係**冷**嘅 → 一下子 miss 打落 DB。做法：逐台加、預熱、或者過渡期新節點 miss 時回查舊節點。
- **有狀態數據更麻煩**：緩存搬咗只係 miss，但計數器 / session / 限流窗口搬咗等於**狀態歸零**，要雙讀、遷移或者接受短暫誤差。
- **對比 Redis Cluster**：Redis 用固定 16384 個槽 + 明確嘅槽分配表，遷移逐槽做（`MIGRATING`/`IMPORTING` + `ASK` 重定向），可控、可手動 rebalance；一致性雜湊冇中心分配表，但搬乜 key 由 hash 決定，唔容易精細控制。
- **變種**：Jump Consistent Hash（唔使存環、好均勻，但只適合喺尾部加減節點）、Bounded-load（限制每節點負載唔超過平均 ×(1+ε)，熱點溢出去下一個）、Rendezvous（HRW）hashing。

### 常見追問 / 陷阱

「多個客戶端點樣保證路由一致？」→ 每個客戶端嘅節點列表一定要一致。配置推送有延遲時，同一個 key 會被唔同客戶端送去唔同節點 → 數據分裂、計數唔準。節點列表要由註冊中心統一下發，帶版本號；變更期間預期有短暫不一致，業務要容忍或者雙寫。
