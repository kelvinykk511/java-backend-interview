# 分散式：CAP 與 BASE

## 面試問題

CAP 定理怎麼講？為什麼常說「只能三選二」？實際系統（例如 CEX 下單／帳本）通常怎麼取捨？BASE 又是什麼？

## 模範答案（面試可講）

- **C (Consistency)**：每次讀到的都是最新寫入（強一致視角）。
- **A (Availability)**：每個非故障節點都能在合理時間內回覆（不保證是最新）。
- **P (Partition tolerance)**：網路分區時系統仍能繼續運作。
- 真實網路**一定會有分區**，所以工程上多半是在 **CP vs AP** 之間選，而不是真的「丟掉 P」。
- **CP**：分區時寧可拒絕／等待，也不回過期資料（例如部分共識／強一致儲存）。
- **AP**：分區時仍回應，之後用衝突解決／對帳收斂（例如多數快取、部分 DNS／最終一致註冊中心）。
- **BASE**：Basically Available、Soft state、Eventually consistent —— 用**最終一致**換可用與規模；搭配補償、對帳、冪等。
- CEX 後端常見：撮合／資金核心偏 **強一致 + 嚴格冪等**；行情、非關鍵展示可偏 **最終一致**。

## 常見追問／陷阱

- CAP 的 C ≠ ACID 的 C；面試別混成一句「資料庫有事務就滿足 CAP 的 C」。
- 「我們系統同時滿足 CAP」通常是話術；要講清**在什麼邊界、什麼延遲假設下**你選了哪邊。

## 深入（2026-11-07）：柔性事務、最終一致同 CEX 取捨

### 面試問題

「柔性事務」係咩？同 ACID／2PC／TCC 點區分？最終一致系統靠咩手段收斂（補償、對帳、Outbox、冪等）？CEX 邊啲必須強一致、邊啲可以用最終一致？

### 答法

**柔性事務（面試口徑）**

- 唔係資料庫引擎提供嘅嚴格 ACID 跨服務事務，而係**業務層**接受中間態可見，用補償／重試／對帳令系統**最終**回到正確狀態。
- 對應 BASE：Basically Available（分區時仍可服務）、Soft state（中間狀態允許存在）、Eventually consistent（遲早收斂）。
- 口訣：**用可接受嘅暫時不一致，換可用性同吞吐；用工程手段保證最終帳平。**

**同 ACID／2PC／TCC／Saga 點分**

| 手段 | 一致強度 | 特點 | 代價 |
|------|----------|------|------|
| 單庫 **ACID** | 強 | 本地事務，邊界清晰 | 跨服務唔直接適用 |
| **2PC／XA** | 強（跨資源） | prepare 期間鎖資源 | 吞吐差、協調者故障難搞；高併發少用 |
| **TCC** | 業務層偏強控制 | Try 凍結 → Confirm／Cancel | 每個動作要幂等；空回滾／懸掛要處理 |
| **Saga／補償** | 最終一致 | 每步本地提交，失敗逆序補償 | 中間態可見；補償本身要幂等 |
| **Outbox + MQ** | 最終一致 | 本地事務綁業務+outbox，異步可靠投遞 | at-least-once → 下游必須幂等 |
| **對帳／補償工單** | 最終一致兜底 | 定時比對、補單、人工／自動糾偏 | 滯後窗口內可能睇到不一致 |

詳見 [2PC／TCC／Saga](distributed-transaction-tcc-saga.md)、[Transactional Outbox](transactional-outbox.md)、[冪等](idempotency.md)。

**最終一致要齊嘅四件套**

1. **冪等**：重試／重複消息唔雙花、唔雙入帳（業務唯一鍵、狀態機）。
2. **可靠投遞**：Outbox／本地消息表，保證「庫成功 ⇒ 事件最終會出」。
3. **補償**：失敗走反向業務（解凍、退款、加返額度），唔係 DB rollback。
4. **對帳**：日終／近實時對帳係**最後防線**——發現缺口就補單或告警，唔好假設 MQ 永遠完美。

**CEX 邊強邊柔（常考）**

| 場景 | 傾向 | 原因 |
|------|------|------|
| 撮合成交、資金／持倉帳本、凍結／解凍、出金扣款 | **強一致／TCC 思路** | 錯帳＝真金白銀；要嚴格狀態機 + 幂等 |
| 充值入帳通知風控／積分／推送、行情、非關鍵展示 | **最終一致（Outbox／Saga）** | 可重試、可對帳；短暫延遲可接受 |
| 跨機房「寫帳本」用純 AP | **危險** | 分區兩邊都接受寫 → 雙花／負餘額／對唔平；資金面通常要 CP 或單主 + 明確拒絕 |

面試講法：唔係成個系統「選 AP」或「選 CP」，而係**按邊界拆**——資金核心偏 CP／強一致；周邊讀模型、通知偏 AP／最終一致，再用對帳收斂。

### 追問／陷阱

- CAP 嘅 C ≠ ACID 嘅 C：前者講副本讀寫可見性；後者講事務四性質。唔好混。
- 「我哋用咗微服務所以一定最終一致」→ 錯。可以單服務內強一致、跨服務柔性；亦可以 TCC 把關鍵路徑控到接近業務強一致。
- 「柔性事務＝可以唔對帳」→ 錯。柔性更依賴對帳同補償；冇對帳就係賭運氣。
- 跨機房寫資金帳本若選 AP：分區時兩邊都寫成功 → 合併時衝突；資金場景通常**拒絕寫**（偏 CP）或固定單主，而唔係 silently 最終一致。
